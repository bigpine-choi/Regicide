# 전이표 메모리 재사용: 비용 감소와 같은 시간 대국

## 결론

**반복 검색의 비용은 줄었고, 규칙과 고정 깊이의 탐색 동작은 유지됐다. 같은 시간 대국의 경기력 향상은 확인하지 못했다.** 준비 검색 후 깊이 1 요청 시간의 중앙 가속은 3.72배, 깊이 3은 1.37배였다. 총 250쌍에서 수·점수·깊이·노드·PV·기존 TT 작업량이 모두 같았다.

| 이전 v0.4.0 대비, 각 8시작×선후공 16판 | v0.4.1 승/무/패 | 득점률 |
| --- | ---: | ---: |
| 같은 요청 40ms/수 | **5 / 6 / 5** | **50.0%** |
| 같은 요청 100ms/수, 환경 중단 후 전체 재측정 | **4 / 5 / 7** | **40.6%** |

100ms 표본에서는 개선 버전의 득점이 더 낮았다. 속도 향상을 경기력 향상이라고 표현하지 않는다. 작은 고정 개발 표본이므로 이 결과를 일반적인 강도 차이나 Elo로 환산하지 않는다. 기준 버전은 별도 브랜치·소스와 실행 파일로 보존했다.

첫 100ms 묶음은 PC의 유휴 절전 중단과 겹쳐 **6승 2무 7패·미완료 1판**으로 끝났다. 실패를 보존하고 사전에 [환경 복구·재측정 계획](2026-10-17-hash-memory-retry-plan.md)을 추가한 뒤 같은 엔진·설정으로 전체 16판을 한 번 다시 실행했다. 원래 완료된 15판을 주 비교에 합치지 않았다.

## 버전·사전 계획·환경

[원래 계획](2026-10-17-hash-memory-plan.md)과 엔진·도구를 비계측 결과 전에 커밋했다. 평가 계수·안정화 대상·TT의 깊이/경계/교체 정책과 Hash 기본값을 유지했다. 실험 중 엔진·도구를 수정하지 않았다. 결과·재현·환경 기록만 후속 커밋에 추가한다.

| --- | --- | --- |
| 엔진 | Regicide 0.4.0 | Regicide 0.4.1 |
| 소스 | `ef52f14569222acbfaa512245bab81558795180f` | `4a0f95a035b1cc0eff8e8d56a14ea898621eab64` |
| 실행 파일 SHA256 | `620cdba22750978898809e32711cb117a0f4f74a08a6ab8dffe7de9046ba5340` | `0bac627c4b7eb8425e6812a64dad5546ed1a7e24dd603cb365f12dd569ffd2e9` |

기준을 `git archive`로 별도 `build-memory-baseline/source/`에 추출해 빌드하고, 개선도 코드 고정 후 전체 재빌드했다. 독립 감사에서 관련 소스 내용과 바이너리 해시를 대조했다. 감사자가 바이너리를 독립 재빌드했다는 뜻은 아니다. PE 타임스탬프 때문에 재빌드 해시는 달라질 수 있다.

- 2026-10-17, Asia/Seoul. AMD Ryzen AI 7 350, 논리 CPU 16개, RAM 약 31.3 GiB, Windows 11 x64.
- 양쪽 동일 MSVC 19.51.36260.0, C++20 `/O2 /DNDEBUG /W4 /WX /permissive- /utf-8`, 단일 탐색 작업 스레드.

- 모든 벤치마크·대국은 각각 단독 실행했다. 재현용 부하 검사는 첫 대국 묶음이 중단된 뒤, 재측정 전에 종료했다.
- 세 벤치마크와 원래 두 대국은 `4a0f95a`, 재측정은 문서 계획만 추가한 `1836ca5`에서 시작했다. 각 시작 시 체크아웃은 깨끗했고 엔진·도구 코드는 동일했다. 결과는 무시되는 `build/task05-evidence/`에 먼저 저장했다.

## 변경과 정확성

UCI 세션이 `SearchContext`를 소유해 같은 크기의 표를 유지한다. 매 검색은 새 세대이며 다른 세대의 점수·최선 수·깊이는 읽지 않는다. 옵션·이력 변경을 오래된 점수의 재사용과 분리한다. 최초 사용·실제 크기 변경에만 새 할당하며, 새 대국·Clear Hash는 저장 공간을 유지한다. 세대 번호 순환 때는 물리적 전체 정리로 옛 기록의 재등장을 막는다. [원리·작은 체스 예·API](../HASH_MEMORY_REUSE.md)에 자세히 설명했다.

MSVC 네이티브 별도 실행에서 이전·개선의 슬롯이 모두 **56바이트**, Hash 16 MiB에서 **299,593개·16,777,208바이트**임을 확인했다. 세대 필드는 기존 정렬 여유에 들어가 용량과 슬롯 주소 계산을 유지한다. [소스](../profiles/2026-10-17-hash-memory/tt-layout-probe.cpp)와 [결과](../profiles/2026-10-17-hash-memory/tt-layout-probe.jsonl)를 남겼다.

기존 보드와 반복 규칙·규칙 테스트 파일은 변경하지 않았다. 새 검사에서는 이력·FEN·카운터·평가/안정화/TT/빠른 적용 옵션·Hash 크기·중단·새 대국·명시적 초기화·세대 순환 후 새 컨텍스트와 정확히 같은 탐색 동작을 확인했다. TT 비활성·종료 검색은 버퍼를 사용하지 않으며 통계 0은 프로세스 전체 보유 메모리를 뜻하지 않는다.

## 고정 깊이 시간 비용

기존 10개 위치를 그대로 사용했다. 시드 20261017로 순서를 섞고 각 쌍의 엔진 순서를 교대한다. 매 표본 새 대국을 알리되 UCI 프로세스는 유지한다. `--require-same-search`로 점수·최선 수·완료 깊이·노드·seldepth·PV·TT 조회/적중/차단/저장의 일치를 요구했다. 준비 검색은 기록하되 주 측정에서 제외했다.

| 조건 | 측정 쌍 | 쌍별 벽시계 가속 중앙값 | 합산 벽시계 기준→개선 | 빨라진 쌍 |
| --- | ---: | ---: | ---: | ---: |
| 깊이 1, 준비 검색 없음 | 100 | 4.1015배 | 0.374338→0.098720초 | 100/100 |
| 깊이 1, 준비 1회 | 100 | **3.7234배** | 0.435357→0.118955초 | 100/100 |
| 깊이 3, 준비 1회 | 50 | **1.3662배** | 0.500668→0.369906초 | 49/50 |

세 조건의 측정 노드 합계는 양쪽 각각 **7,550 / 7,550 / 170,370개**로 같았다. 수·점수·PV·TT 작업량도 전부 같았으며, 모든 위치의 시간 중앙값은 개선됐다. 깊이 3의 한 표본은 느렸다. 각 표본 시간 비율의 중앙값과 합산 시간의 비율은 다른 통계다.

‘준비 없음’도 새 프로세스의 최초 한 요청만 할당하고 이후 99회는 버퍼를 재사용한다. 첫 요청만의 기준/개선 시간은 **4.4376/4.1412ms**였고 엔진당 단 한 표본이다. 4.10배를 최초 할당의 가속이라고 해석하지 않는다. 준비 검색을 한 조건은 준비 과정에서 한 번 할당하고 주 측정에서는 할당이 없었다.

| 개선 버전의 측정 구간 | 할당 | 재사용 | 물리적 전체 정리 | 최대 사용 바이트 |
| --- | ---: | ---: | ---: | ---: |
| 깊이 1, 준비 없음 | 1 | 99 | 0 | 16,777,208 |
| 깊이 1, 준비 1회 | 0 | 100 | 0 | 16,777,208 |
| 깊이 3, 준비 1회 | 0 | 50 | 0 | 16,777,208 |

기준 v0.4.0은 새 메모리 통계를 보고하지 않으므로 원자료에서 ‘없음’을 유지했다. 매 검색 할당한다는 설명은 기준 소스의 구현에 근거한다. 물리적 전체 정리와 세대 번호만 바꾸는 논리적 초기화를 구분한다.

깊이 1 개선판은 두 조건 모두 100회 중 99회가 정수 밀리초의 0을 보고했다. 주 지표는 UCI 요청·대국 재설정·응답을 포함한 고해상도 벽시계이며 프로세스 시작 시간은 제외한다. 반복 횟수는 독립 위치나 경기력 표본 수를 늘리지 않는다. 세 벤치마크는 절전 진입 전에 모두 끝나 중단 영향을 받지 않았다.

원자료: [깊이 1·준비 없음](../profiles/2026-10-17-hash-memory/depth1-cold.json), [깊이 1·준비 1회](../profiles/2026-10-17-hash-memory/depth1-warm.json), [깊이 3·준비 1회](../profiles/2026-10-17-hash-memory/depth3-warm.json). [독립 감사](../profiles/2026-10-17-hash-memory/benchmark-independent-audit.md)에서 250쌍과 준비 검색을 포함한 728개 PV수·순서·해시·옵션·출처를 재검증했다.

## 같은 시간 실제 대국

기존 8개 시작 수순·선후공 교대, 전체 이력 전달, 현재/예정 수 반복·50수 청구를 항상 처리하는 정책, 500반수 안전 한도를 유지했다. 대국 전 준비 검색은 없고 최초 할당도 해당 수의 예산에 포함한다. 내부 탐색 시간은 양쪽 요청 40/100ms에서 동일하게 **20/80ms**다.

| 주 비교, 각 16판 | 승/무/패 | 기준/개선 평균 완료 깊이 | 기준/개선 평균 노드/수 | 기준/개선 평균 벽시계 |
| --- | ---: | ---: | ---: | ---: |
| 40ms | 5 / 6 / 5 | 3.862 / 4.005 | 12,623 / 14,039 | 21.887 / 21.281ms |
| 100ms 전체 재측정 | 4 / 5 / 7 | 4.224 / 4.269 | 32,868 / 33,916 | 82.733 / 81.698ms |

주 비교 32판은 모두 정상 종료했다. 21판 메이트, 11판 올바른 예정 수 3회 반복 청구였고 불법 수·오류·시간 초과·한도 중단은 없었다. [독립 감사](../matches/2026-10-17-hash-memory/primary-audit-summary.md)로 **3,725반수·15,845 PV수**를 재생해 수순·결과·청구·선후공·해시·자원을 확인했다. [40ms PGN](../matches/2026-10-17-hash-memory/time40.pgn)·[JSON](../matches/2026-10-17-hash-memory/time40.json), [100ms 재측정 PGN](../matches/2026-10-17-hash-memory/time100-retry.pgn)·[JSON](../matches/2026-10-17-hash-memory/time100-retry.json)을 보존한다.

같은 시간에서 평균 노드와 완료 깊이는 늘었지만 수순이 달라져 위치 분포도 다르다. 이를 고정 위치 NPS나 전략적 판단의 개선으로 해석하지 않는다. 40ms 득점은 동률이고 100ms는 기준보다 낮아 이번 표본에서 경기력 향상은 입증되지 않았다.

8개 시작 쌍을 묶어 20,000회 재표집한 참고 득점 범위는 40ms **34.4..65.6%**, 100ms **28.1..50.0%**였다(시드 20261017). 작고 고정된 표본의 기술적 부트스트랩이며 보편적인 강도 신뢰구간이 아니다. JSON의 Wilson 값도 무승부·짝지은 표본의 독립 베르누이 가정을 만족하지 않아 강도 추정에 쓰지 않았다.

## 첫 100ms 중단과 복구

원래 100ms 묶음은 16번 대국 99반수 뒤 개선판 흑 차례에 `TimeoutError`가 났다. 해당 판은 `*`이고 15판만 완료됐다. [원래 PGN](../matches/2026-10-17-hash-memory/time100.pgn)·[JSON](../matches/2026-10-17-hash-memory/time100.json)과 [미완료 감사](../matches/2026-10-17-hash-memory/independent-audit-summary.md)를 별도 보존한다. 실패한 요청은 반환 수의 평균 시간에서 제외되므로 정상 응답 평균으로 이 실패를 감추지 않는다.

[시스템 기록](../matches/2026-10-17-hash-memory/suspend-events.json)은 22:28:38.181 유휴 Modern Standby 진입과 22:40:57.226 재개를 보여준다. 실패 대국의 723.5초 경과와 이 중단 기간이 겹친다. 정확한 수순·FEN·새/재사용 프로세스·이전/개선 버전의 재현 **110회**는 모두 정상 응답했고 최대 약 82.24ms였다. [재현 결과](../matches/2026-10-17-hash-memory/debug/raw-reproduction.json)·[결론](../matches/2026-10-17-hash-memory/debug/conclusion.json)을 남겼다. 절전으로 인한 외부 중단이라는 해석을 지지하며 엔진 멈춤은 재현되지 않았다.

복구 계획을 커밋한 뒤 첫 결과를 덮어쓰지 않고 100ms 전체 16판을 한 번 재측정했다. 실행 중에만 [Microsoft 실행 상태 API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate)로 유휴 절전을 억제했고 영구 전원 정책·화면 켜짐 요구는 바꾸지 않았다. [반환·복원 기록](../matches/2026-10-17-hash-memory/wake-guard.json)에서 종료 코드 0과 이전 상태 복원을 확인했고, 재측정 기간 [절전 이벤트](../matches/2026-10-17-hash-memory/retry-suspend-events.json)는 없었다. 두 실행의 유불리를 보고 고르거나 원래 완료 15판을 주 비교에 합치지 않았다.
