# 프로파일링·전이표: 비용과 같은 시간 32판

## 결과와 범위

**규칙 검증을 유지하면서 탐색 시간 비용이 줄었고, 이 고정 표본의 같은 시간 대국에서도 이전 v0.3보다 높은 득점을 기록했다.** 전체 최적화와 전이표 하나의 효과를 나누어 측정했다.

| 측정 | 실제 결과 |
| --- | --- |
| 이전 v0.3 → 개선 v0.4, 고정 깊이 3 | 10위치×5회, 쌍별 요청 시간 가속 중앙값 **21.96배**, 점수 50/50 일치 |
| 개선 버전 안에서 TT 끔 → 켬, 깊이 4 | 같은 10위치×5회, 중앙값 **1.60배**, 점수 50/50 일치, 총 노드 **31.3% 감소** |
| 양쪽 40ms/수, 8시작×선후공 16판 | 개선 **15승 1무 0패**, 득점률 **96.9%** |
| 양쪽 100ms/수, 같은 16판 | 개선 **15승 0무 1패**, 득점률 **93.8%** |

기준 상대는 자체 기초 엔진이며 위치도 작은 개발 표본이다. 이 결과로 Elo나 강한 외부 엔진·인간 상대 경기력을 추정하지 않는다. 시간 측정의 5회 반복은 경기력 검증 표본을 늘린 것이 아니다. 전이표는 일부 위치에서 오히려 느렸다.

## 사전 고정과 출처

[계획](2026-10-17-profile-transposition-plan.md)과 엔진·도구·시작 위치를 비계측 벤치마크·대국 결과 전에 커밋했다. 평가 수식과 안정화 탐색 규칙은 바꾸지 않았다. 대국 결과를 본 뒤 계수·기본 Hash·위치·판수를 조정하지 않았다.

| 항목 | 기준 | 개선 |
| --- | --- | --- |
| 엔진 | Regicide 0.3.0 | Regicide 0.4.0 |
| 소스 | `3869db0fc2a575c25ad8026cf022733708f76b08` | `df045565042442e5684ec4c9d36e495aaa39d086` |
| 비계측 Windows 실행 파일 SHA256 | `818c9938ee18cdfcaecd49db6b6f068ed022bfd7f7682ce7a7f85c54c76f9d8d` | `29036c3a66cc06952a122bfd322354c242243e8e89513a747c24289eaf14c12d` |

기준은 `git archive`로 별도 `build-profile/baseline-source/`에 추출해 원래 빌드 스크립트로 빌드했다. 개선도 코드 커밋 후 전체 재빌드했다. 기록된 해시와 해당 소스 내용을 독립 대조했다. 이는 감사자가 실행 파일을 별도로 재빌드했다는 뜻은 아니다. 빌드 타임스탬프 때문에 재빌드 실행 파일 해시는 달라질 수 있다.

두 벤치마크와 두 대국 실행 모두 시작 시 체크아웃이 깨끗했음을 JSON에 저장했다. 엔진·도구 소스는 이후 바꾸지 않았으며, 생성 결과는 무시되는 `build/task04-evidence/`에 먼저 저장한 뒤 이 문서와 함께 보존했다. 감사 중에는 결과 설명 문서와 복사한 증거만 미추적 상태였다.

## 실행 환경과 자원

- 2026-10-17 Asia/Seoul; JSON의 시각 표기는 각 도구의 필드 참고.
- AMD Ryzen AI 7 350 w/ Radeon 860M, 논리 CPU 16개, RAM 약 31.3 GiB, Windows 11 x64.
- 비계측: 양쪽 MSVC 19.51.36260.0, C++20 `/O2 /W4 /WX /permissive- /utf-8`. 개선은 생성 수 경로의 디버그 재검사를 끄는 Release `/DNDEBUG`도 사용한다. 기준 소스에는 해당 assert 경로가 없다.
- 프로파일: WSL Ubuntu 24.04, GCC 13.3, `-std=c++20 -O2 -DNDEBUG -pg`, gprof 0.01초 표본. 시간 배수는 이 계측 실행에서 계산하지 않았다.
- Python 3.13.16, `chess==1.11.2`. 각 엔진의 탐색 작업 스레드 1개. 모델·학습·GPU·오프닝 북 없이 자체 코드가 수를 고른다.
- 대국·속도 측정끼리는 동시에 실행하지 않았다. 위치 평가·안정화는 양쪽 켬. 개선의 빠른 수 적용 켬, TT 기본 16 MiB. 테이블 할당 시간도 요청·탐색 시간에 포함한다.

## 발견한 병목과 재계측

같은 [드라이버](../../scripts/profile_search.cpp)의 4위치×30회×5,000노드, 총 600,000노드를 계측했다. 전체 이력이 있는 오프닝, Kiwipete, 룩 엔드게임을 포함했다. 동일 노드 수라도 TT와 수 순서 때문에 방문한 트리가 완전히 같지는 않다.

| 호출 | 기준 | 개선 | 관찰 |
| --- | ---: | ---: | --- |
| 합법 수 생성 내부 함수 | 5,807,712 | 600,130 | 중복 검증·앙파상 정규화·불가능한 예정 청구 검사 제거 |
| 킹 체크 검사 | 200,716,693 | 18,786,652 | 중복 수 생성과 후보 검증 감소 |
| 상태용 FEN 출력 | 4,677,824 | 0 | 반복 판정을 정확한 고정 상태로 보관 |
| 실제 탐색 노드 | 600,000 | 600,000 | 같은 작업 예산 |

기준 flat profile의 자기 시간은 체크 검사 58.02%, 합법 수 생성 17.81%, 수 후보 추가 13.23%, FEN 출력 5.11%였다. 이미 합법 목록에서 고른 수를 `play()`로 적용하면서 전체 목록을 다시 만들고, 지고 있는 말단에서 반복 청구가 불가능해도 수들을 시험한 비용이 컸다. [구현 원리](../PERFORMANCE.md)에 안전한 생략 조건과 정확한 반복 판정을 설명했다.

계측 자기 시간 합계 5.67초→0.76초는 표본·계측 영향을 받으므로 실제 가속 배수로 제시하지 않는다. 원시 [기준 flat](../profiles/2026-10-17/baseline-flat.txt)·[callgraph](../profiles/2026-10-17/baseline-callgraph.txt), [개선 flat](../profiles/2026-10-17/candidate-flat.txt)·[callgraph](../profiles/2026-10-17/candidate-callgraph.txt), 두 driver 출력과 [환경·명령 기록](../profiles/2026-10-17/environment.json)을 보존했다.

## 고정 깊이 비계측 비교

`tests/data/profile_positions.json` 전체 10개를 5회씩, 시드 20261017로 순서를 섞고 쌍별 실행 순서를 교대했다. 매 요청 전에 새 대국을 설정하며 프로세스 시작은 제외하고 UCI 요청·응답과 테이블 초기화는 포함했다. 100쌍 모두 완료 깊이·정확한 점수·합법 최선 수/PV를 확인했다. 최선 수도 모든 쌍에서 같았다.

| 지표 | v0.3 → v0.4 깊이 3 | v0.4 TT 끔 → 켬 깊이 4 |
| --- | ---: | ---: |
| 쌍별 벽시계 가속 중앙값 | 21.9611배 | 1.5971배 |
| 합산 벽시계 | 17.1502 → 0.6940초 | 5.9626 → 4.3289초 |
| 합산 노드 | 199,635 → 170,370 | 2,346,070 → 1,611,370 |
| 노드 비율의 중앙값 | 0.7970 | 0.5683 |
| TT 조회/적중/차단 | 개선 8,510 / 1,570 / **0** | 켬 84,180 / 7,915 / **1,790** |
| 빨라진 표본 | 45/50 | 40/50 |
| 상세 | [depth3.json](../profiles/2026-10-17/depth3.json) | [tt-depth4.json](../profiles/2026-10-17/tt-depth4.json) |

중앙 가속은 각 표본의 `기준 시간 / 개선 시간`의 중앙값이며 합산 시간의 비율과 다르다. 깊이 3은 캐시 **점수 차단이 없었으므로** 21.96배를 전이표의 점수 재사용 효과라고 부를 수 없다. 중복 규칙 계산 제거와 수 정렬의 결합 효과다. TT만 비교한 깊이 4의 총 노드는 31.3% 줄었다. 위의 노드 중앙 비율은 별도 통계다.

깊이 3 위치별 중앙 가속은 초기 배치 1.90배, Open Game 41.98배, Queen Pawn 32.82배, Sicilian 30.67배, French 42.85배, Caro-Kann 30.13배, QGD 17.62배, Reti-English 10.13배, 재캡처 예 2.55배, 폰 엔드게임 **0.45배**였다. 깊이 4 TT 단독 비교에서도 Reti-English **0.89배**, 폰 엔드게임 **0.51배**로 느렸다. 작은 트리에서는 16 MiB 초기화 부담이 크고 수 정렬도 항상 유리하지 않다. 밀리초 정수로 보고된 시간이 0인 표본은 엔진 시간 비율에서 제외하고, 벽시계 원자료는 유지했다.

## 같은 시간 실제 대국

기존 8개 시작 수순을 그대로 사용하고 각 위치의 선후공을 바꿨다. 전체 이력을 전달하고 가능한 현재/예정 수 3회 반복·50수 청구는 항상 처리했다. 500반수 안전 한도, 오류·한도 중단은 완료 무승부로 바꾸지 않는 기존 정책이다.

| 요청 시간/수, 각 16판 | 개선 승/무/패 | 기준/개선 평균 완료 깊이 | 기준/개선 평균 노드/수 | 기보·상세 |
| --- | ---: | ---: | ---: | --- |
| 40ms | **15 / 1 / 0** | 1.376 / 3.195 | 443.5 / 8,191.8 | [PGN](../matches/2026-10-17-tt/time40.pgn), [JSON](../matches/2026-10-17-tt/time40.json) |
| 100ms | **15 / 0 / 1** | 1.718 / 3.784 | 1,268.9 / 32,203.3 | [PGN](../matches/2026-10-17-tt/time100.pgn), [JSON](../matches/2026-10-17-tt/time100.json) |

양쪽 기본 Move Overhead 20ms를 유지해 내부 탐색 할당은 각각 **20/80ms**다. 평균 벽시계 응답은 40ms 조건 기준/개선 21.526/22.145ms, 100ms 조건 81.771/82.463ms였다. 이번 1,950개 엔진 선택 수에서 보고 탐색 시간이 내부 할당을 넘거나 벽시계가 요청 시간을 넘은 수는 없었다. 일반적인 실시간 보장을 뜻하지는 않는다.

32판 모두 종료했고 오류·한도·미실행은 0건이다. 31판 메이트, 1판 예정 수 `e8b8`에 의한 올바른 3회 반복 청구였다. 독립 감사로 **2,134반수와 5,930 PV수**의 합법성, PGN/JSON·결과·시작 쌍·해시·자원 통계를 재확인했다. [감사 보고서](../matches/2026-10-17-tt/independent-audit-summary.md)와 세부 JSON·감사 스크립트도 보존했다.

8개 시작 쌍을 묶어 20,000회 재표집한 참고 득점 범위는 40ms **90.6..100%**, 100ms **81.3..100%**였다(시드 20261017). 고정된 작은 표본의 기술적 부트스트랩이며 보편적인 강도의 신뢰구간이 아니다. JSON의 Wilson 참고값도 무승부·짝지은 위치의 독립 베르누이 가정을 만족하지 않으므로 강도 추정에 쓰지 않았다. 대국 결과는 여러 최적화를 합친 효과이며 TT 하나의 승률 기여도를 분리하지 못한다.

## 유지한 검증과 재현

| 실제 수행 검사 | 결과 |
| --- | --- |
| 기존 규칙/perft | 20그룹 / 8,325개, 기존 테스트 파일 변경 없음 |
| 외부 규칙 기준 | `chess==1.11.2`와 2,997사례, 기존 테스트 변경 없음 |
| 탐색 / 평가 | 23그룹 / 885개, 6그룹 / 400개 |
| 보드 상태 / 전이표 | 8그룹 / 11,927개, 5그룹 / 73개 |
| UCI / 대국 / 비교 / 벤치마크 도구 | 10그룹 / 11사례 / 10사례 / 7그룹 |
| Windows | 전체 스크립트 빌드, 깨끗한 CMake/CTest 5/5 |
| Linux | GCC 엄격 Release 전체 5검사, Debug ASan·UBSan 보드·탐색·전이표 통과 |
| 원격 자동 검사 | Windows·Ubuntu 전체 CI 통과 ([코드 커밋 실행](https://github.com/bigpine-choi/Regicide/actions/runs/39035526383)) |

기존 CMake 출력 폴더를 재사용하는 과정에서 링크 잠금과 오래된 객체를 사용한 검사 실패가 있었고, 새 폴더 전체 빌드 및 기존 폴더 `--clean-first` 재빌드로 모두 통과했다. 실험 실행 파일은 항상 전체 컴파일하는 스크립트로 만들었다. 별도 GCC `-O1` sanitizer 빌드는 `std::optional` 관련 미초기화 경고로 멈췄지만, 엄격 Release `-O2`와 실제 Debug `-O0` sanitizer 실행은 통과했다.

비계측 비교 재현 예시는 다음과 같다. 기준 파일은 위 기준 커밋으로 별도 빌드해야 한다.

```powershell
.\.venv-tests\Scripts\python.exe scripts/benchmark_search.py build-profile/baseline-source/build/regicide.exe build/regicide.exe --output build/recheck-depth3.json --depth 3 --repeats 5 --baseline-commit 3869db0fc2a575c25ad8026cf022733708f76b08 --candidate-commit df045565042442e5684ec4c9d36e495aaa39d086
.\.venv-tests\Scripts\python.exe scripts/benchmark_search.py build/regicide.exe build/regicide.exe --output build/recheck-tt.json --depth 4 --repeats 5 --baseline-options '{"UseTranspositionTable":false}' --baseline-commit df045565042442e5684ec4c9d36e495aaa39d086 --candidate-commit df045565042442e5684ec4c9d36e495aaa39d086
.\.venv-tests\Scripts\python.exe scripts/compare_engines.py build-profile/baseline-source/build/regicide.exe build/regicide.exe --movetime 40 --pgn build/recheck-time40.pgn --baseline-commit 3869db0fc2a575c25ad8026cf022733708f76b08 --candidate-commit df045565042442e5684ec4c9d36e495aaa39d086
```

`--movetime 100`으로 보조 조건을 재현한다. 시간 기반 수순과 결과는 스케줄링에 따라 달라질 수 있다. 이후 과제는 표 메모리 재사용의 초기화 비용, 보류 위치와 강한 상대의 효과 검증이다. 신경망·학습과 복잡한 죽은 포지션의 일반 판정은 이번 범위에 포함하지 않았다.
