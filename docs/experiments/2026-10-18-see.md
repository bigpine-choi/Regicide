# SEE v0.5.2: 교환 순서와 같은 시간 대국

**같은 깊이의 탐색 노드는 약 16% 줄었다. 요청 100ms와 1초의 개발 비교에서는 모두 우세했다.** 작은 재사용 표본과 관측된 사용자 엔진의 동시 부하를 고려해 일반적인 강도 향상은 추가 검증한다.

기준은 PVS v0.5.1 `1441d5ec23733af570b05521620935619c39cefa`, 후보는 v0.5.2 `0edc06e437b934d177fc1e9b0907600b6287be72`다. [사전 계획](2026-10-18-see-plan.md)을 `0c4bb32c77b782c594be31f49e0344be16191227`에서 먼저 고정했다. 계측 경계와 점수 차이 중단 가드도 측정 전에 명시했다. 결과를 본 뒤 엔진·평가·시작 위치·시간·판수를 조정하거나 유리한 결과로 교체하지 않았다.

## 구현과 검증

[SEE](../SEE.md)는 목적지에서 가장 싼 합법 공격자로 번갈아 되잡는 지역 교환 손익을 추정한다. 핀·왕 안전·열리는 공격선·앙파상·승격을 반영하며 원본 보드와 반복 이력을 바꾸지 않는다. **수 정렬에만 적용**하고 음수 교환의 희생 수도 계속 탐색한다. 평가·PVS·안정화의 수 범위·전이표 격리·시간 관리는 유지했다. `UseSEE=false`는 이전 정렬 경로를 사용한다. 외부 엔진 코드나 가중치는 가져오지 않았다.

Windows MSVC와 Linux GCC 13.3 Release에서 각각 규칙 20그룹·8,325검사, 탐색 42그룹·13,579검사, 평가 6그룹·400검사, 보드 10그룹·18,974검사, 전이표 8그룹·97검사, SEE 8그룹·3,438검사를 통과했다. Linux는 CMake 미설치로 직접 strict-warning 빌드했으며, ASan/UBSan에서도 탐색·SEE 전부 통과했다. 최초 환경 오류 로그도 보존한다.

SEE 독립 검사는 생산 코드의 공격 판정이나 swap 역산을 재사용하지 않고 합법 수 API와 재귀 계산으로 45위치·1,442수(음수 교환 57, 승격 8, 앙파상 1)를 대조했다. 퀸 희생 `Qxg8+ Rxg8 Nf7#`처럼 음수 SEE가 승리하는 수를 일반·안정화 탐색 모두에서 보존한다. 최초 새 정렬 테스트의 a5 폰이 실제로 룩에 보호되는 위치 오류를 발견해 a4로 수정했다. 이 실패는 측정 전에 해결했고 원본 로그를 보존한다.

기존 python-chess 규칙 차등 2,997사례, UCI 19그룹, 대국/비교/비용 도구 11/10/9, 사용자 대국 25, 핸디캡 19, 기보 보관 20(Windows 심볼릭 링크 권한으로 1개 건너뜀), 부트스트랩 3검사를 유지했다. Godot 4.7.2 headless 장면 검사도 입력·시점 637, 실제 연결 75, 종료 3사례, 핸디캡 53, 기보 78검사를 통과했다. 이번의 직접 수동 GUI 검증으로 확대하지 않는다. 동결 소스의 [Windows·Ubuntu GitHub CI](https://github.com/bigpine-choi/Regicide/actions/runs/39053937624)도 모두 성공했다.

## 환경과 동결

AMD Ryzen AI 7 350(8코어·16논리 CPU), RAM 33,598,976,000바이트, Windows 11 Home 10.0.26200, MSVC 19.51.36260.0 C++20 `/O2 /DNDEBUG`, Python 3.13.16, chess 1.11.2다. 양측 단일 탐색 스레드·Hash 16MiB·Move Overhead 20ms·PVS 켬이다. 후보만 SEE를 켰다. 요청 100/1,000ms의 내부 할당은 80/980ms다.

기준을 해당 커밋의 별도 소스 아카이브에서, 후보를 깨끗한 동결 체크아웃에서 같은 MSVC 플래그로 재빌드했다. 기준 SHA256은 `c333ccfa7ec3efbaa7f52df4c007875e64f68d0816a847c1390aa3213d0e427b`, 후보는 `2ba41c8303f266149323b55186f5c6a806c33f73d529d6911d6ca4b33bfa53db`다. [환경·소스 해시](../matches/2026-10-18-see/provenance.json)를 보존한다. 측정 동안 엔진 소스와 바이너리는 바뀌지 않았다.

빌드·Linux 검사와 다른 에이전트의 엔진 작업을 끝낸 뒤 비용→끔 대조→100ms→1초를 순차 실행했다. 전체 실행은 종료 코드 0이며 임시 절전 억제의 이전 상태 복구도 성공했다. 사용자 대국 창·개인 기보·바탕화면의 안정 v0.5.0 설치본은 보존했다. 비교 기준 v0.5.1과 바탕화면 설치본은 구분한다.

## 같은 깊이 계산 비용

기존 10개 개발 위치 × 5회, 깊이 3·4 각각 50쌍이다. seed 20261018로 위치 순서를 섞고 기준/후보 실행 순서를 교대했다. 엔진별 첫 워밍업 1회는 요약에서 제외했으며, 새 대국 신호·전체 이력과 재사용하는 프로세스로 전이표 상태를 통제했다.

| 깊이 | 전체 노드 기준 → SEE | 노드 감소 | 쌍별 벽시계 가속 중앙값 | 해당 시간 감소 |
|---|---:|---:|---:|---:|
|3|262,675 → 221,325|15.74%|1.030781배|2.99%|
|4|1,046,725 → 882,885|15.65%|1.077756배|7.21%|

SEE 켬 100쌍의 점수 차이는 0이다. 끔 대조 100쌍도 선택 수·점수·노드·PV·기존 TT 계측이 모두 같았다. 끔 대조 벽시계 가속 중앙값은 깊이별 1.006339/1.015042배로, 작은 시간 차이에는 측정 변동이 있다. 전체 노드 합계 비율과 쌍별 시간 비율 중앙값은 서로 다른 통계다.

SEE 계산 자체에도 비용이 들어 노드 감소만큼 빨라지지는 않았다. 위치별 쌍 시간 비율 중앙값에서 깊이 3은 Initial/Sicilian/Caro-Kann/Opposed pawn endgame, 깊이 4는 Defended rook recapture/Opposed pawn endgame이 느려졌다. 역할별 절대 시간 중앙값을 따로 비교하면 깊이 3의 Defended rook recapture도 느려져, 통계별 차이도 원자료에 남긴다. 모든 위치와 반복은 [원자료](../matches/2026-10-18-see/)에 남겼다. 공통 python-chess 파서는 마지막 `info string`인 TT 계측을 보존하므로 별도 SEE 호출 수는 이 JSON에 수집하지 않았다. 호출 계측은 C++/UCI 검사에서 검증했다.

## 같은 요청 시간 대국

이전 PVS 비교와 같은 8개 시작 수순에서 선후공을 바꿔 조건별 16판을 진행했다. 이전 개발에 사용된 위치이며 새로운 보류 표본이 아니다. 전체 수순을 전달하고 현재/예정 수의 반복·50수 무승부는 청구하며 최대 500반수다. Python은 통신·규칙·기보를 담당하고 두 자체 C++ 엔진이 수를 선택했다.

## 동시 부하와 계측 한계

실행기는 사용자 엔진을 강제 종료하지 않고 시작 전 유휴 확인과 실행 중 CPU 스냅샷을 보존했다. 실제 다른 사용자 엔진의 계산도 관측됐으므로 배타적인 PC 실험이라고 주장하지 않는다. 기록된 부하와 구간은 [별도 CPU 감사](../matches/2026-10-18-see/external-load-audit.md)에 남겼다. 완료한 결과를 유리한 재실행으로 교체하지 않았다.

실제 외부 엔진 20244/7408에서 각각 18.375/224.9375 CPU초 증가를 관측했다. 스냅샷 끝점의 단계별 분류에서 고정 깊이 비용 중 외부 증가 0, 유휴 확인 2.875초, 100ms 대국 6.828125초, 1초 대국 233.609375초였다. CPU초는 벽시계 지연과 동일하지 않다. 특히 시간 대국은 이 동시 연산과 스케줄링의 영향을 받을 수 있어 깨끗한 부하에서의 재검증이 필요하다.

또한 Windows 가상환경의 Python 실행기가 실제 Python 자식 프로세스를 한 번 더 거치는 것을 실행기의 직접 부모 PID 필터가 놓쳤다. 그 결과 두 비교 엔진도 외부 목록에 포함되어 원본 `observed_external_engine_cpu_increase`는 과대 보고된다. 원본은 수정하지 않고 당시 프로세스 부모 관계 증거와 정확한 두 실행 경로를 사용한 별도 분류를 제공한다. 실제 사용자 엔진의 부하까지 오분류로 제거하지 않는다. 5초 간격 스냅샷은 완전한 스케줄러 추적이나 전체 PC 부하 측정이 아니다.

## 감사·재현과 다음 판단

[독립 감사](../matches/2026-10-18-see/independent-audit.md)는 엔진을 실행하지 않고 시작 수순 포함 실제 3,648반수와 대국 PV 20,372수를 재생했다. 최종 FEN·종료 이유·선후공·득점·옵션·버전·소스와 바이너리 해시·깨끗한 동결 상태를 확인했다. [기계 판독 감사](../matches/2026-10-18-see/independent-audit.json)와 원본 JSON/PGN·빌드·검증·실행 상태를 함께 보존한다. 개인 사용자 기보는 포함하지 않았다. 원자료는 Git 줄바꿈 변환 없이 보관한다.

SEE는 개발 후보의 기본 수 정렬과 켬/끔 대조로 유지한다. 이번에 확인한 것은 계산 비용 감소와 이 두 개발 대국 표본의 우세다. 안정 대국 설치본 교체와 일반적인 강도 확정에는 배타적인 부하 아래 더 많은 새로운 시작 쌍 검증이 필요하다. SEE 가지치기는 도입하지 않았다.

재현은 동결 후보의 별도 깨끗한 체크아웃에서 시작한다. 기준 1441d5e를 `build-see-baseline/source/`에 git archive로 추출해 그 안의 `scripts/build.ps1`로 빌드한다. 후보는 `scripts/build.ps1 -BuildDirectory build-see-native -Test`로 빌드하고 테스트용 Python 환경을 준비한다. 기존 출력은 덮어쓰지 않는다.

```powershell
./scripts/run_see_comparison.ps1 -CandidateCommit 0edc06e437b934d177fc1e9b0907600b6287be72
$env:PYTHONIOENCODING='utf-8'
./.venv-tests/Scripts/python.exe tests/audit_see_results.py build/see-evidence --candidate-commit 0edc06e437b934d177fc1e9b0907600b6287be72 --output build/see-evidence/independent-audit.json
```

동시 부하 감시의 직접 부모 필터 한계는 위 설명과 함께 해석한다. 시간 대국 수순과 재빌드 실행 파일 해시는 환경에 따라 달라질 수 있으므로 각 새 실행의 버전·해시를 별도로 기록한다. 이번 실험에서는 강한 외부 상대나 Elo를 평가하지 않았다.
