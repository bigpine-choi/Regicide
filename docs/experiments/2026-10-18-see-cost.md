# SEE 비용 개선 v0.5.3: 손실 분석과 수정 전후 비교

**SEE 함수 비용은 줄였지만, 경기력 향상은 두 시간 조건에서 일관되게 확인되지 않았다.** 수정 전 SEE v0.5.2 대비 새 8위치의 100ms는 **5승 3무 8패(40.625%)**, 1초는 **5승 7무 4패(53.125%)**였다. 같은 깊이의 전체 탐색 시간은 작고 혼재된 차이를 보였다. 따라서 v0.5.3을 검증된 경기력 강화나 안정판으로 승격하지 않는다.

이번 수정은 SEE가 계산하는 교환 값과 수의 우선순위를 유지하면서 계산 비용을 줄이는 데 집중했다. SEE 함수만 반복 호출한 통제 측정에서는 호출 시간 비율의 중앙값이 기존 대비 약 **18~20% 감소**했다. 이 수치를 전체 엔진의 속도나 경기력 향상으로 해석하면 안 된다. 개발 위치에서 계측한 기존 탐색의 SEE 시간 비중은 약 **7.17%**였고, 안정화 탐색 노드가 전체의 **92.19%**였다. 전체 탐색 비용과 대국 결과는 별도로 비교했다.

기존 SEE의 762번 수 선택 가운데 완료 깊이 4 이하인 10회는 모두 패배한 판에 있었다. 그러나 전체 평균 완료 깊이는 SEE **6.479**, 상대 PVS **6.332**였고, PVS에도 깊이 4 이하 선택이 18회 있었다. 따라서 이 관찰만으로 “SEE 비용 때문에 항상 얕아져서 졌다”고 결론 내리지 않는다. 최대 선택 깊이는 일부 길게 이어진 경로의 깊이이며, 작업 전체가 그만큼 깊게 탐색됐다는 뜻도 아니다.

아래는 분석에 사용한 구체적인 위치다. cp는 폰 1개를 100으로 둔 **해당 엔진 자신의 평가**다. 평가 급락은 의심 구간을 찾는 단서이며, 독립 엔진의 최선 수 판정이나 객관적인 실수 확정이 아니다.

1. **게임 11, 45반수, 백 23.Kg2**

   FEN: `2r2rk1/Q2n2b1/1p4p1/p2Pn2p/P1P2p1q/1PN4P/3BB3/2R2RK1 w - - 2 23`

   완료 깊이 4·선택 깊이 28에서 -102cp를 보고했다. 공개 PV는 `Kg2 Qg3+ Kh1 Qxh3+ Kg1`이었다. Qg3+를 받은 뒤 다음 자기 차례, 즉 **24.Kh1을 고르는 시점**에는 ...f3를 예상하며 -865cp를 보고했고, 실제 대국도 `Kg2 Qg3+ Kh1` 뒤 **조용한 f3**로 이어졌다. 8개의 실제 반수 뒤 기물 차이는 +10cp에서 -490cp로 변했다. 체크 수순 사이에 끼는 조용한 공격을 더 깊게 읽어야 하는 사례다. Kg2 대신 어떤 수가 최선인지는 이 분석에서 확정하지 않았다.

2. **게임 12, 40반수, 흑 20...Nb6**

   FEN: `2r2rk1/1p1n1pb1/6p1/p1pPn2p/P1P1P2q/2N1B2P/1P1QB1K1/R4R2 b - - 1 20`

   완료 깊이 4·선택 깊이 31에서 -4cp, PV `Nb6 Rf4 Qg5+ Rg4`를 보고했다. 실제 백은 **Bg5**로 퀸을 공격했고, 다음 흑 차례의 자기 평가는 -218cp였다. 같은 칸에서의 교환 손익을 잘 계산하는 것과 여러 칸에 걸친 조용한 위협을 찾는 것은 구분해야 한다.

3. **게임 4, 92반수, 흑 46...Qxa4**

   FEN: `8/p4p2/1p5k/3PK3/R4P2/8/6Q1/3q4 b - - 2 46`

   완료 깊이 6에서 -35cp였고, PV는 `Qxa4 Qg5+ Kh7 Kf6 Qd4+ Kxf7`이었다. 실제 백의 다음 수 Qg5+에서 백 엔진은 5수 메이트를 보고했고, 다음 흑 차례에도 메이트 패배를 인식했다. 룩을 얻는 국소적인 교환 이익이 왕의 안전을 보장하지 않는 사례다. 앞선 선택 중 어디부터 패배가 강제됐는지는 별도 검증이 필요하다.

[분석 코드](../matches/2026-10-18-see-cost/analysis/analyze_archived_losses.py), [전체 결과](../matches/2026-10-18-see-cost/analysis/archived-loss-analysis.json), [개발 위치 16개](../matches/2026-10-18-see-cost/analysis/development-positions.json)에 전체 실제 수 이력·FEN·기물 차이·평가·깊이·PV·응수의 캡처/체크 여부를 보존한다. 초기 수기 설명에서 게임 10의 Nxe5를 조용한 Ne5로, Qb8을 체크로 잘못 적었던 부분은 교정했다. 최종 SAN과 캡처·체크 분류는 python-chess 재생 결과를 따른다.

## 이번에 수정한 것

SEE(Static Exchange Evaluation, 한 칸에서 교대로 잡고 되잡을 때의 기물 손익 추정)는 수 정렬에만 사용한다. 이번 변경은 그 추정값이나 가지치기 조건을 바꾸지 않는다.

- **칸별 공격 기하를 미리 계산했다.** 폰·나이트의 출발 후보와 8방향 광선 목록을 64칸에 대해 만든다. 교환 중에는 실제 점유 상태만 다시 확인해, 같은 좌표 계산과 가장자리 검사를 반복하지 않는다. 가려진 룩·비숍·퀸의 공격선은 점유 상태가 달라질 때 계속 반영한다.
- **공격자 전체 정렬을 줄였다.** 폰 최대 2개·나이트 최대 8개·광선당 첫 공격자 최대 8개라는 기하 상한을 사용해 작은 목록을 만든다. 가장 싼 합법 공격자를 먼저 고르고, 핀 때문에 움직일 수 없으면 상태를 복원한 뒤 다음 후보를 확인한다. 기물 가치가 같으면 출발 칸 번호가 낮은 수를 고르는 기존 규칙을 유지한다.
- **왕 안전 검사를 조기에 끝낸다.** 왕이 공격받는지 확인할 때는 모든 공격자를 저장하지 않고 하나만 발견하면 끝낸다. 핀에 걸린 상대 기물도 왕의 이동을 금지하는 기하 공격으로 세는 기존 규칙을 유지한다.
- **사용하지 않는 임시 저장 공간 초기화를 없앴다.** 교환 손익 배열은 실제로 작성한 구간만 읽는다. 앙파상의 다른 칸 폰 제거, 승격 이익, 왕 재포획, 불법 재포획 시 복원은 유지한다.
- **정렬에 기여하지 않는 SEE 호출을 생략했다.** 후보 수가 0~1개이면 정렬할 필요가 없다. 이전 탐색/PV/전이표에서 가져와 독립된 최상위 그룹을 차지하는 preferred 수도 교환 값을 계산해 다른 수와 비교할 일이 없다. 두 경우 모두 취소 확인을 유지한다. `see_calls`는 실제로 교환 함수를 호출한 횟수다.

합법 수 생성, 평가 함수, 안정화 탐색이 허용하는 수, 가지치기는 변경하지 않았다. 따라서 이번 가설은 **같은 탐색 결정을 더 적은 비용으로 처리해 제한 시간 안에서 추가 탐색 여유를 얻을 수 있는가**다. 기존 기보의 모든 전술·엔딩 약점이 이번 변경으로 해결됐다는 가설은 아니다.

## SEE 비용 프로파일에서 확인한 것

[프로파일 명세](../matches/2026-10-18-see-cost/profile/core-manifest.json)와 [통제 측정](../matches/2026-10-18-see-cost/profile/loss-scenes-profile-guarded.json)은 파싱·합법 수 생성·값 대조를 시간 측정 밖에 두고 SEE 함수 호출 자체를 비교한다. 같은 실행 파일에 이전 SEE와 수정 SEE를 함께 넣고 9회 순서 교대 측정했다. 이전 SEE 소스와 수정 SEE의 개별 질의 값도 대조했다.

| 개발 자료 | 질의 수 | 반복 조건 | 수정/기존 시간 비율의 쌍별 중앙값 | 해석 |
|---|---:|---|---:|---|
| 패배 장면 16위치 | 43 | 질의당 100,000회 × 9쌍 | 0.80036 | 호출 시간 약 19.96% 감소 |
| 혼합 회귀 95위치 | 359 | 질의당 10,000회 × 9쌍 | 0.82240 | 호출 시간 약 17.76% 감소 |

혼합 회귀에서는 9쌍 중 2쌍이 더 느렸다. 위 수치는 쌍별 시간 비율의 중앙값이며, 각각의 ns 중앙값을 나눈 값과 같다고 가정하지 않는다. 합계 402개 질의의 이전/수정 SEE 값 대조와, 합법 수 재귀 오라클을 사용한 SEE 검사 9그룹·9,119검증은 이 프로파일 단계의 확인 사항이다. 최종 전체 규칙 회귀의 통과 판정과는 구분한다.

기존 탐색에 시계를 넣은 [별도 측정](../matches/2026-10-18-see-cost/profile/loss-scenes-search-profile-detailed-guarded.json)은 개발 16위치 × 3회 × 50,000노드, 총 **2,400,000노드**를 사용했다. 그중 안정화 노드는 **2,212,635개(92.193%)**, SEE 호출은 **2,006,700회**였다. 계측된 SEE 시간은 **410,319,800ns**, 전체 계측 탐색 시간은 **5,719,157,000ns**로 약 **7.174%**였다.

이 결과의 한계는 세 가지다. 첫째, SEE 함수의 약 18~20% 단축이 전체 탐색 시간의 같은 비율 단축을 의미하지 않는다. 둘째, 매 호출의 시계 측정 자체가 비용을 더하므로 7.17%는 비계측 실전 바이너리의 정확한 비중이 아니다. 셋째, 안정화 노드 92.19%는 **노드 개수 비중**으로, 실행 시간 92.19% 또는 불필요한 노드 92.19%라는 뜻이 아니다. 계측 검색은 FEN으로 새 반복 이력을 시작한 진단이므로 원대국의 정확한 노드 분포를 재현한 것도 아니다. 별도 비계측 손실 위치 비교에는 전체 실제 수 이력을 전달했다. 이번에는 안정화 수를 잘라내지 않았다.

최종 프로파일과 추가 상세 프로파일은 알려진 외부 엔진 5개의 관측 CPU 증가가 0 native ticks인 구간에서 수행됐다. 초기 비통제 프로파일은 보존하되 최종 통제 비교의 근거와 섞지 않는다. 이 감시는 일반 앱 부하·열·전력 상태나 샘플 사이의 아주 짧은 프로세스 전체를 배제하지 않는다. 프로파일 명세의 `baseline_commit=5148721...`은 당시 저장소 기준 커밋이며, 해당 커밋과 실제 수정 전 엔진 `0edc06e...` 사이의 `src/see.cpp`·`src/search.cpp`는 동일하다. 대국 기준 버전은 위의 0.5.2 소스·바이너리 해시를 사용한다.
