# v0.4.1: 전이표 메모리 재사용

UCI 세션 동안 전이표의 저장 공간을 유지하고, 매 탐색의 기록은 세대 번호로 구분한다. 같은 크기의 표를 반복해서 할당·초기화하던 비용을 줄이는 변경이다. 평가 수식·수 정렬·캐시 점수의 깊이 정책은 v0.4.0을 유지한다. [사전 계획](experiments/2026-10-17-hash-memory-plan.md)과 [실제 비용·대국 결과](experiments/2026-10-17-hash-memory.md)를 함께 읽는다.

## 원리와 작은 예

전이표 항목마다 ‘몇 번째 탐색의 기록인가’를 나타내는 번호를 적는다. 다음 탐색에서 표 전체를 지우는 대신 현재 번호만 올린다. 항목의 번호가 다르면 빈칸으로 취급한다. 따라서 처음 만든 큰 메모리를 다시 쓰면서도 탐색 결과는 새 표로 시작한 것과 같아진다.

예를 들어 백 퀸 d1, 흑 룩 d5, 흑 폰 e6의 위치는 안정화 탐색을 끄면 깊이 1에서 `Qxd5`의 룩 획득을 높게 볼 수 있다. 안정화 탐색을 켜면 폰의 재캡처까지 보므로 값과 선택이 달라진다. 옵션을 바꾼 뒤에는 이전 기록을 읽어서는 안 된다. 세대 번호를 바꾸면 이전 점수와 최선 수를 함께 무효화한다. 이 예와 옵션 전환은 기존 검사에 포함한다.

반복 이력도 중요하다. 나이트들이 전개했다가 돌아온 위치와 같은 FEN을 새로 가져온 위치는 기물 배치가 같아도 반복 횟수가 다르다. 탐색을 시작할 때 새 세대를 쓰고, 탐색 내부에서는 계속 전체 반복 맥락과 50수 카운터를 키에 포함한다.

## 구현과 수명

| 상황 | 동작 |
| --- | --- |
| 첫 활성 검색 | 요청한 Hash 크기로 할당, 이 비용도 검색 시간에 포함 |
| 같은 크기의 다음 검색 | 버퍼 재사용, 세대 번호 증가; 전체 배열 초기화 생략 |
| Hash 크기 변경 | 다음 활성 검색에서 새 버퍼를 만든 뒤 교체; 축소 시 큰 옛 버퍼도 해제 |
| 새 대국·Clear Hash | 기록을 무효화하고 버퍼는 유지 |
| TT 비활성 | 보유 버퍼를 읽거나 새로 할당하지 않음; 다시 켠 검색은 새 세대 |
| 종료 포지션 | 표를 준비하지 않고 기존 종료 결과 반환 |
| 세대 번호 순환 | 전체 항목을 한 번 지운 뒤 1부터 시작; 오래된 1세대 기록 재등장 방지 |
| UCI 종료 | 작업 스레드를 합류한 뒤 컨텍스트와 버퍼 해제 |

세대는 32비트다. 새 검색과 명시적 초기화가 번호를 전진시키며, 최대 번호 다음에는 실제 배열 정리가 필요하다. 경계 검사는 수십억 회 실행하는 대신 검사 전용 접근자로 경계 직전 상태를 만들어 확인한다.

`SearchContext`가 메모리를 소유한다. UCI의 각 Session에 하나씩 있고 전역 공유 상태는 없다. 같은 컨텍스트를 동시 탐색에 공유하지 않는다. `setoption`, `position`, `ucinewgame`, `stop`은 이전 작업이 끝난 뒤 처리한다. `isready`는 기존처럼 탐색 중에도 응답한다.

슬롯 세대가 다르면 이전 기록의 깊이도 교체 판단에서 무시한다. 따라서 옛 깊이 64 결과가 새 탐색의 깊이 1 기록을 막지 않는다. 이번 MSVC 비교에서는 세대 필드가 기존 정렬 여유 공간에 들어가 슬롯 크기 56바이트와 Hash 16 MiB의 299,593슬롯을 유지함을 별도 실행으로 확인했다. 해시 충돌 검사·메이트 거리 보정·정확한 반복 판정은 기존과 같다.

새 할당을 끝낸 뒤 버퍼를 교체하므로 잘못된 크기나 할당 실패로 기존 저장 공간이 먼저 사라지지 않는다. 크기를 바꾸는 동안에는 새 버퍼와 옛 버퍼가 잠시 함께 존재한다. TT를 끄면 기존 버퍼를 보유할 수 있으며 세션 종료 때 해제한다.

## 사용법과 통계

기존 UCI 설정은 유지한다. 새 버튼은 값 없이 호출한다. 각 `go`의 `bestmove` 응답을 받은 뒤 다음 명령으로 진행한다.

```text
setoption name Hash value 16
position startpos
go depth 1
go depth 1
setoption name Clear Hash
go depth 1
```

UCI는 기존 네 통계 뒤에 메모리 작업을 붙인다.

```text
info string tt probes ... hits ... cutoffs ... stores ... allocations ... reuses ... clears ... bytes ...
```

- `allocations`: 이번 호출의 버퍼 할당 횟수. 첫 사용·실제 크기 변경은 1.
- `reuses`: 이번 호출의 기존 버퍼 재사용 여부. 같은 크기의 활성 검색이면 1.
- `clears`: 이번 검색 준비 중 세대 번호 순환으로 전체 배열을 지운 횟수. 일반적인 논리적 초기화는 0이다. 검색 밖에서 호출한 Clear Hash의 작업을 다음 검색에 합산하지 않는다.
- `bytes`: 이번 검색이 사용하는 표의 바이트 수. 비활성·종료 검색은 0이며 프로세스가 보유한 전체 메모리 사용량을 뜻하지 않는다.

C++ 호출자는 같은 컨텍스트를 전달한다.

```cpp
regicide::SearchContext context;
regicide::Board board;
const auto first = regicide::search(board, {.depth = 2}, nullptr, {}, {}, &context);
const auto next = regicide::search(board, {.depth = 2}, nullptr, {}, {}, &context);
context.clear();
```

컨텍스트 인자를 생략한 기존 API는 일회용 표를 사용한다. 콘솔 `regicide search`를 매번 별도 프로세스로 실행하는 경우에는 세션 간 메모리가 남지 않는다.

## 검증과 측정 해석

기존 규칙/perft·외부 기준 검사를 변경하지 않았다. 반복 검색과 새 컨텍스트의 점수뿐 아니라 최선 수·깊이·노드·PV·TT 조회/적중/차단/저장까지 비교한다. 옵션·이력·FEN·카운터·특수 수·Hash 크기·중단·새 대국·세대 순환도 검증한다. 같은 깊이의 탐색은 같고 그 계산에 드는 비용이 달라지는 것이 이번 변경의 목표다.

벤치마크의 `--warmup N`은 준비 검색 N회를 별도 기록해 주 측정에서 제외한다. `--require-same-search`는 이전 버전과 탐색 동작이 다르면 실패한다. 최초 할당과 반복 검색을 나누어 보고하며, 밀리초 단위 엔진 시간이 0인 짧은 요청은 UCI 왕복의 고해상도 벽시계를 주 지표로 삼는다.

시간 비용 감소가 곧바로 승률 증가를 보장하지는 않는다. 같은 시간 대국의 성적은 [실험 기록](experiments/2026-10-17-hash-memory.md)에 별도로 남긴다. 검색 간 점수의 지속적인 공유는 이번 구현에 포함하지 않는다. 자체 작성한 변경이며 새 외부 엔진 코드·모델·데이터를 사용하지 않았다.
