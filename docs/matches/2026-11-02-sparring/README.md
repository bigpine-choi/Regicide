# 스파링 모드 × Stockfish 18 제한 기력: 8판 진단

2026-11-02. **6승·1패·1미완료이며, 50수까지 접전을 유지하는 목표는 충족하지 못했다.** 낮은 세 설정에서는 모두 이겼지만 너무 일찍 끝났다. 가장 강한 설정에서는 한 판을 졌고, 다른 한 판은 110수 상한까지 승부가 나지 않았다. 단계 전환과 기록의 정확성은 확인했지만, 접전 연출·최종 승리·인간 수준 추정의 정확성은 입증하지 않았다.

## 조건과 재현 범위

- 정책: `regicide-sparring-play-v1`. 기능 소스 `28c3efc62ebe1f5b1e2647daac22ea020d39202a`, 검증 도구를 포함한 실제 실행 소스 `fa25aa56895c78d3a42ec7ccc5ac02f325146ef6`의 깨끗한 main.
- 실제 앱의 `HumanGame.new_game(sparring_mode=True)`와 `engine_move`/`human_move`를 사용했다. 갬빗 보스·일반 동적 선택·오프닝 다양성 정책은 꺼졌으며, 착수는 자체 Regicide 엔진과 자체 스파링 정책만 결정했다. 화면용 배경 탐색만 비활성화했다.
- Regicide: 고전 평가 + `UsePieceActivity=True`, 기준 생각시간 1000ms 및 정책 보조 예산 최대 2000ms. 런타임 SHA256 `5011da4c5e6ef01c452bd7125e4e22b372d2c9cfb858ed8759057325acb0e6ba`.
- 상대: 설치된 **Stockfish 18 한 버전의 네 가지 기력 제한 설정**. `UCI_LimitStrength=True`, `UCI_Elo=1320/1700/2100/2500`, 1000ms, Threads=1, Hash=16MiB, Ponder=False. Regicide도 Hash=16MiB이며 자체 단일 스레드 엔진이다. SF SHA256 `9bde420202717ce083412027fbfb8c5c935b537591d712be8a8a8bae92f6e8d6`.
- 두 엔진의 실제 계산 예산은 같지 않다. 따라서 일반 모드와의 동일 자원 기력 비교도 아니며, UCI_Elo 숫자를 사람의 Chess.com·Lichess·FIDE 레이팅으로 환산하지 않는다. 기존 설치 패키지의 GPLv3 라이선스와 출처 기록을 유지했고, 이번 결과물에는 외부 엔진 실행 파일을 재배포하지 않았다.
- 표준 시작 위치, 강제 오프닝·핸디캡 없음. 설정별 백·흑 각 1판, 총 8판. 같은 설정의 색 교대 두 판은 같은 사전 선언 스파링 시드를 사용했다. 전역 시드는 `sparring-validation-2026-11-02-v1`. SF의 내부 무작위 시드 제어는 제공되지 않으므로 재실행의 동일 수순은 보장하지 않는다.
- 1320/1700 묶음과 2100/2500 묶음을 동시에 실행했다. Windows 11 Home, AMD Ryzen AI 7 350, 8코어/16논리 프로세서, 사용 가능한 총 메모리 약 31.3GiB. [장비 기록](hardware.json), [30초 간격 부하 표본](load-samples.json) 18개에서 전체 CPU 0~37%, 여유 메모리 최저 약 10.7GiB였다. 이는 순간 표본이며 외부 부하의 부재나 각 프로세스의 CPU 시간을 증명하지 않는다.
- 체크메이트·규칙상 종국만 승패로 인정하고, 청구 가능한 3회 반복·50수 무승부는 항상 청구한다. 평가값으로 조기 종료하지 않는다. 상한은 220반수=110수이며 `*` 미완료로 보존한다. 엔진 오류를 승리로 처리하지 않는다.

유효 상대 관측은 247개였다. 내부 추정치와 목표가 증가·감소하는 기록은 있으나, 추정치가 변화했다는 사실만으로 상대 수준을 정확히 측정했다고 볼 수 없다.

## 접전과 후반 전환

접전의 사전 정의는 유한한 정확 평가에서 `절댓값 <=150cp`였다. 메이트·불완전·경계 평가를 임의의 cp로 바꾸지 않고 분모에서 제외했다. 여기서 정확 평가는 UCI에서 경계값이 아닌 점수라는 뜻이며, 체스의 객관적 정답이라는 뜻은 아니다.

- 첫 50수 구간의 **자체 선택 수 평가**: 확인 가능한 256위치 중 175위치(68.4%)가 접전 범위였다. 대상 착수 283개 중 27개는 사용할 수 있는 유한한 점수가 없었다.
- **SF 보조 기준**: 스파링 착수 후 SF가 탐색한 다음 위치에서 205개 유효 점수 중 92개(44.9%)가 접전 범위였다. 대상 SF 착수 280개 중 75개는 제외했다.
- 두 지표는 탐색 주체·시점·스케일이 달라 한 집단으로 합산하지 않는다. SF의 `play` 정보는 여러 탐색 반복이 합쳐질 수 있으며, 점수는 SF의 약화된 실제 선택 수에 대한 평가가 아니다. 외부 엔진 점수는 진단 기록에만 사용했고 스파링 착수에 공급하지 않았다.
- 특히 2500 설정의 초반 50수 구간은 자체 기준 77/86(89.5%), SF 다음 위치 기준 24/76(31.6%)였다. 동일 위치·동일 계산량 비교가 아니므로 이것만으로 평가 오차를 수치화할 수는 없다. 다만 자체 게이지가 접전이라고 표시하는 비율만으로 목표 달성을 선언해서는 안 된다.

100반수에 도달한 판은 마지막 1판뿐이었다. 그 판에서 실제 `ramp` 결정 20회(102~140번째 반수), `finish` 결정 40회(142~220번째 반수)를 확인했다. finish 구간은 모두 기준수를 사용했고 보조 예산이 0이었다. **단계 전환의 정상 동작을 확인한 것이며, 후반에 실제 승리하거나 강도가 충분히 높아졌다는 검증은 아니다.** 후반의 실제 양보는 이미 0회였다.

실측 스파링 호스트 처리 시간은 평균 약 1380ms, 중앙값 1284ms, 95백분위 1893ms, 최대 2727ms였다. 이는 저장·호스트 처리까지 포함한 벽시계 시간이며 엔진 CPU 시간과 다르다.

## 확인된 병목과 다음 가설

현재 정책은 상대가 평균적으로 잃는 평가량을 참고해 작은 양보를 고른다. **현재 형세를 접전 범위로 돌려놓는 별도 조절기가 없다.** 상대가 한 번에 큰 실수를 하면 우세는 크게 벌어지지만, 실력 추정치는 천천히 변하고 안전 상한은 그 우세를 유지한다. 불안정 평가·허용 후보 부재·메이트 보호가 합쳐져 대부분 기준수를 선택했다.

예를 들어 1320 첫 판 17반수에서는 상대의 직전 손실이 149cp이고 기준수 평가가 +203cp였다. 후보 `Be3`는 같은 깊이에서 +92cp로 검증됐지만 손실 111cp가 당시 목표 약13cp 및 허용 상한을 넘어서 제외됐다. 다음 큰 실수 이후에도 같은 구조가 반복됐다. 이 사례는 후보가 없어서만 아니라 조절 목표 자체가 다르기 때문에 접전 복원이 제한됨을 보여준다. 해당 원본 수순과 점수는 압축 기록의 `ratings-1320-1700/game-001.json`에 남아 있다.

다음 검증 가설은 **실력 추정과 형세 조절을 분리**하는 것이다. 실력 모델은 완만하게 유지하되, 50수 이전에는 자연스러운 검증 후보 중 현재 우세를 작은 양수 범위로 유지하는 수를 비교한다. 같은 위치의 오프라인 비교로 큰 기물 헌납·패배 전환·반복을 먼저 확인하고, 별도 시드와 동일 조건의 새 대국으로 접전율과 승리 가능성의 상충을 측정해야 한다. 이 가설은 이번 버전에 적용하거나 시험하지 않았다. 평가 게이지의 점수를 균형처럼 꾸미지 않는다.

8판·설정당 두 판은 기능 진단 표본이다. 일반 모드 대조군이 없고 적응형 정책과 추가 예산이 있으므로 Elo 추정·학습 효과·자연스러운 인간 체감·승리 보장·안정적인 경기력 우위를 주장하지 않는다.

## 검증과 재실행

대국 하네스의 합성 회귀 검사 8개, 집계 회귀 검사 13개가 통과했다. 실제 8판의 수순·색·최종 위치·종국·모드·판단 이력과 저장된 PGN/JSON을 독립 재생했다. 두 실행 묶음 모두 소스·오프닝 자료·실행 파일 해시가 시작과 끝에 동일했다. 압축 후 원본 60개 파일을 각각 다시 읽어 SHA256과 일치함을 확인했다.

```powershell
.venv-tests/Scripts/python.exe scripts/sparring_strength_match.py --binary <기록된 Regicide.exe> --stockfish <Stockfish18.exe> --ratings 1320 1700 --seed sparring-validation-2026-11-02-v1 --expected-source-commit fa25aa56895c78d3a42ec7ccc5ac02f325146ef6 --expected-binary-sha256 5011da4c5e6ef01c452bd7125e4e22b372d2c9cfb858ed8759057325acb0e6ba --output-dir <새 A 폴더>
.venv-tests/Scripts/python.exe scripts/sparring_strength_match.py --binary <기록된 Regicide.exe> --stockfish <Stockfish18.exe> --ratings 2100 2500 --seed sparring-validation-2026-11-02-v1 --expected-source-commit fa25aa56895c78d3a42ec7ccc5ac02f325146ef6 --expected-binary-sha256 5011da4c5e6ef01c452bd7125e4e22b372d2c9cfb858ed8759057325acb0e6ba --output-dir <새 B 폴더>
.venv-tests/Scripts/python.exe scripts/summarize_sparring_match.py <A 폴더/match.json> <B 폴더/match.json> --output <새 집계.json>
```

소스 재현 시에는 별도 체크아웃에서 기록된 실행 커밋을 사용한다. 현재 개발 폴더의 기존 수정사항을 되돌려 재현하지 않는다. 원본 압축을 풀면 위 두 match.json과 개별 상세 기록의 상대 경로가 유지된다. `summary.json`의 절대 입력 경로는 실제 실행 당시의 위치를 보존한 것이다.
