# 갬빗 자동 시계: 대기 시간의 자체 검증 전환

기존 호스트는 검색을 끝낸 뒤 결과가 불안정하면 표시상 생각 시간을 늘렸다. 추가된 대기 시간에는 계산하지 않았다. 이번 변경은 갬빗 모드의 자동 시계에서만, 위험한 선택을 자체 엔진으로 다시 검사하는 데 기존 대기의 일부를 쓴다. 새 C++ 연속 전술 후보의 효과와 별개다.

## 적용 조건과 제한

- 시계가 진행 중이고 10초 이상 남아 있어야 한다. 이미 한 재검증, 사용자 강제 수가 있는 대국, 빠른 응수·정해진 오프닝은 제외한다.
- 실제 검색의 완료 깊이별 수·평가가 불안정하거나 긴 생각 대상으로 분류되고, 선택한 수가 명백한 기물 노출·위험한 포획·즉시 메이트 허용에 해당할 때만 검사한다. 이 기하 판단만으로 수를 바꾸지 않는다.
- 기존 가시 목표에서 이미 쓴 시간과 150ms 마감을 뺀 범위, 현재 시계의 비축 시간, 최대 6000ms 중 가장 작은 값만 쓴다. 600ms 미만이면 생략한다.
- 기존 자체 `sparring_safety.verify`를 재사용한다. 원래 수 뒤 상대 응수, 대안들을 제한한 원래 국면, 대안 뒤 상대 응수를 순서대로 검색한다. 완료 깊이와 정확한 점수·합법적인 예상 수순을 확인하고, 대안의 원래 국면/응수 뒤 평가가 일치하며 개선이 충분할 때만 교체한다. Stockfish를 수 선택에 쓰지 않는다.
- 원래 가시 마감을 고정한다. 시계 편집은 마감을 줄일 수 있으나 늘릴 수 없다. 종료·시계 소진·대국 변경을 감시하며, 불충분한 근거나 실패는 기존 합법 수를 유지한다. 시간 초과 후에는 어떤 늦은 수도 적용하지 않는다.
- 검사 이후 추가 표시 대기를 하지 않는다. 선택 이유와 검증 자료를 기보에 보존하고, 해당 결과를 시간 조건이 다른 정책 메모에 재사용하지 않는다.

## 실제 기존 실행 파일 재현

실행 파일 SHA256: `5011da4c5e6ef01c452bd7125e4e22b372d2c9cfb858ed8759057325acb0e6ba`. 앱의 기존 classical activity 평가, 단일 스레드 자체 엔진을 사용했다. 새 C++ 연속 전술 기능은 이 실행 파일에 없다. 아래 두 실행은 시간제 단일 국면 진단이며 CPU를 격리하지 않았다.

최소 국면:

```text
kb4rr/pp6/4p3/2R2p2/1P1Pq3/P3BR1P/8/5Q1K w - - 7 37
```

실제 대국의 선택은 `37.Rc8`이었다. 그때 기본 검색 요청은1156ms였고, 검색 후 가시 목표는7730ms, 대기 시작 전 사용 시간은1711.334ms, 이후 계산 없는 대기는6031.279ms였다. 백은 이미 크게 불리한 국면이었다.

개인 기보의72플라이 이력과 당시 시계·선택 자료를 로컬 메모리 및 자동 삭제되는 임시 폴더에서 사용했다. 공개 자료에는 위 FEN, 짧은 선택, 이력의 해시와 길이만 넣었다. 원시 이력·기보는 포함하지 않았다.

1. **새 호스트 전체 경로**: 당시 seed·72플라이 이력·시계 잔액·이전 판단 자료를 복원하고 `HumanGame.engine_move`를 실제 실행했다. 이번 기본 검색은1123ms 요청에서 `Bf4`를 골랐다. 원대국의 `Rc8` 재현과 구분한다. 이후 기존 가시 목표7732ms 안에서5912ms를 검사에 배정했다. 실제5893.922ms 검사 뒤 `Rc3`로 바뀌었고 추가 대기는0.011ms였다. 자체 검사는 Bf4 뒤 -1041cp, Rc3 원래 국면/응수 뒤 모두 -714cp를 얻었다.
2. **저장된 Rc8 이후의 새 호스트 경로**: 당시 `Rc8` 선택과 검색 후 계획, 이미 사용한1711.334ms의 시계 상태를 복원했다. 기본 검색을 새로 했다고 주장하지 않는다. `_recheck_gambit_idle`과 이후 대기 경로는 실제 엔진/실제 경과 시계로 실행했으며 강제 sleep이나 예산 확대는 없었다. 자동 배정5867ms, 실제5849.140ms 검사에서 `Rc8`→`Rc3`로 바뀌었다. 원수의 상대 응수 검색은 깊이6/-874cp, 대안 검색은 깊이7/-714cp, 대안 뒤 응수는 깊이6/-714cp였다. 추가 대기는0.012ms였다.

두 실행의 [최소 검증 기록](host-idle-replay.json)을 보존했다. 이 자료는 이전에 `sparring_safety.verify`만 직접 호출한6000ms 실험과 다르다. 당시 별도 사후 비교에서 Rc8은 Stockfish18의 -M12, Rc3은 -837cp였지만 이 값은 이번 수 선택에 입력되지 않았다. Rc3도 크게 불리하며, 한 국면의 개선을 전체 기력·Elo 향상 또는 메이트 방지 보장으로 해석하지 않는다.

## 회귀 검사

실행 환경: 로컬 Windows, 저장소 `.venv-tests` Python, python-chess. 외부 엔진을 쓰지 않는 제어된 자체 엔진 응답으로 호스트의 배분·선택·취소 경로를 검사했다.

- `tests/gambit_recheck_tests.py`:15개 통과. 대기/비축 한도, 적용 제외 조건, 실제 refine 연결, 세 단계 자체 검색의 교체와 저장, 검증 실패 시 유지, 정상 모드 보존, 낮은 시계, 종료·시계 삭감·증가·소진·대국 무효화 등을 확인했다.
- `tests/engine_pacing_tests.py`, `tests/sparring_safety_host_tests.py`, `tests/sparring_safety_tests.py`: 합계54개 통과.
- `git diff --check`: 통과.

새 검사는 CI의 기존 `gambit_*tests.py` 발견 검사에서 실행된다. 개인 전체 대국을 회귀 입력으로 저장하지 않았다.
