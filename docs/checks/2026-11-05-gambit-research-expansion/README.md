# 갬빗 분기 연구·기억 병합·집중 재연구

2026-11-05, 한국 시간. 기준 커밋 `2a344c6f1efb2ef3170ae2dcf8631514627573dc`. 상대의 추가 방어를 이어 연구하고, 원본을 보존하며 기억을 합치고, 필요한 위치를 더 높은 예산의 새 연구로 연결했다. **연구 도구의 기능·자료 보존을 검증한 결과이며 기력 상승 검증은 아니다.**

## 변경 내용

1. **여러 응수의 후속 연구:** 상대의 원래 최선 응수를 제외한 자체 검색으로 추가 방어를 고른다. 분기한 전체 이력에서 내 후속 수와 상대 응수를 연구한다. 기본 한 갈래 동작을 유지하며, 분기 수·연습 길이·전체 논리적 노드 상한을 제한한다. 추가 응수 검색의 제한된 점수를 원래 후보의 무제한 평가로 사용하지 않는다.
2. **보수적 기억 병합:** 같은 엔진·평가기에 속한 검증된 기억을 새 폴더에 모은다. 기준 파일을 보존하고 같은 상태·수의 다른 근거는 충돌로 보류한다. 점수·깊이만으로 기존 근거를 교체하지 않는다. 입력별 출처와 원본 바이트 사본을 남기며 기존 실전 재검증 조건을 유지한다.
3. **집중 연구 준비:** 기존 연구의 특정 기록, 같은 완료 깊이 후보의 작은 점수 차이, 공통 후보의 평가 변화, 또는 PGN에서 직접 고른 위치를 새 시작점으로 만든다. 후보 점수·깊이·전체 이력을 원래 질의와 대조하고 보류 계열·위치 키를 이어받는다. 자체 점수는 정답이 아니라 선정 근거로만 사용한다.

[분기 연구 사용법](../../GAMBIT_LINE_RESEARCH.md), [병합](../../GAMBIT_MEMORY_MERGE.md), [집중 연구](../../GAMBIT_FOCUSED_RESEARCH.md). 현재는 명령행 연구 도구다. 대국 화면·핵심 C++ 검색·기존 갬빗 정책·활성 기억·가중치를 바꾸지 않았다. 반복 체크를 탐색 끝까지 읽지 못하는 기존 핵심 엔진 문제는 이번 구현 범위가 아니다.

## 자동 검사와 검토

최종 **92개 검사**가 통과했다. 기존 연구 21개, 분기 연구 9개, 제한 질의 13개, 기억 병합 16개, 집중 연구 13개, 기존 기억 10개, 기존 검색 어댑터 10개다. 중복된 테스트 ID가 없는지 확인했다. [검증 요약](unit-verification.json)과 ZIP 안 원시 테스트 출력을 보존했다.

전체 기보·합법 수·특수 수, 제한 목록 정규화, 반환 수의 제한 집합 포함 여부, 캐시 재사용·손상·입력 불일치, 여러 번의 재개, 분기 및 전체 예산, 원본 파일 보존, 충돌 및 후보 상한, 로더 호환성, PGN/기록 선정, 점수의 질의 근거 연결, 보류 영역의 누적 보존을 확인했다.

첫 검색 어댑터 검사 명령은 파일을 직접 실행해 저장소 모듈을 찾지 못했다. 올바른 `python -m unittest discover` 호출로 바꾸어 10개를 통과했다. 이 호출 오류와 로그도 보존했으며 이미 통과한 82개를 다시 돌리지는 않았다.

독립 코드 검토에서 추가 갈래의 후속 연구 순서, 제한 점수의 컴파일 경계, 이전 연구의 holdout 선언 누락, 저장 점수와 질의의 연결 부족을 보완했다. 최종 재검토에서는 진행을 막는 결함을 발견하지 못했다.

## 실제 엔진의 기존·새 방식 비교

사전에 고른 King's·Benko·From의 세 시작 위치를 사용했다. Benko·From은 보류 계열로 계속 제외한다. 이는 교육 자료의 축소본이며 전체 갬빗 학습이나 미사용 계열 평가가 아니다.

- 기준/후보 모두 Regicide 0.7.0-dev, 고전 활동성 평가, Hash 16MiB, LMR 활성
- 실행 파일 SHA256: `5011da4c5e6ef01c452bd7125e4e22b372d2c9cfb858ed8759057325acb0e6ba`
- 검색당 100,000노드, 각 시작 위치의 소유자 2차례, 후보 2개, 시드 20261105
- 실제 엔진 옵션·하드웨어·시간 제한·실행 순서·입력 및 실행 소스 해시는 사전 명세에 보존
- 기존 사용자 GUI 엔진을 유지한 채 검사 엔진만 순차 실행했으므로 경과시간은 속도 비교로 해석하지 않음

| 실행 | 새 검색 | 재사용 | 논리적 요청 노드 | 연습 기록 / 갈래 |
| --- | ---: | ---: | ---: | ---: |
| 기존 코드 한 갈래 | 18 | 0 | 1,800,000 | 6 / 3 |
| 새 코드 한 갈래 | 18 | 0 | 1,800,000 | 6 / 3 |
| 새 코드 두 갈래 연속 | 30 | 0 | 3,000,000 | 9 / 6 |
| 두 갈래 중단 후 재개 | 중단 전 4 + 재개 후 26 | 4 | 전체 3,000,000 | 9 / 6 |

한 갈래의 기존·새 실행은 18개 질의의 수·점수·깊이·노드·PV와 실제 연습 수순·후보 기록이 같았다. 두 갈래 연속·재개 실행도 30개 결과가 같았고 완료 검색의 재계산은 0회였다. 시간과 원시 로그 위치만 내용 비교에서 제외했다. 제한 목록, 추가 응수, 분기한 전체 이력, 제한 평가의 분리도 검사했다. [분기 비교 요약](branch-summary.json).

두 갈래의 기록 수가 늘어난 비교는 **계산량도 180만에서 300만으로 늘어난 조건**이다. 같은 전체 상한에서의 결과는 따로 확인했다.

| King's, 전체 100만 노드 상한 | 논리적 요청량 | 연습 기록 | 실제 연구한 갈래 |
| --- | ---: | ---: | --- |
| 한 갈래 | 900,000 | 3 | 본선 3차례 |
| 두 갈래 | 1,000,000 | 3 | 본선 2차례 + 대안 1차례 |

같은 상한에서는 기록 수가 증가하지 않았다. 본선의 길이 일부를 다른 방어의 후속 연구에 배분했다. 다음 차례를 온전히 분석할 여유가 없으면 멈추므로 실제 사용량은 상한과 다를 수 있다. 이것만으로 대응 품질이나 기력 향상을 주장하지 않는다.

## 실제 재연구·병합 연결

위 연구에서 사전에 지정한 King's 첫 위치 하나를 골라, 전체 기본 보류 사례 8개를 보존한 새 교육 자료를 만들었다. 기존 세션을 수정하지 않고 검색당 200,000노드·소유자 2차례·후보 2개로 **6회, 요청 상한 합계 1,200,000노드**를 새로 계산했다. 낮은 예산의 질의 재사용은 0회였다.

같은 후보의 점수가 변한 경우에는 양쪽 점수·깊이를 기록했다. 변화 자체를 정답 개선으로 판정하지 않았다. 기존 활성 기억과 두 갈래 연구·새 재연구 결과를 병합한 검토용 파일은 **161개 위치·462개 후보**, 충돌 보류 4건, 정확 중복 4건이었다. 기준 기억은 160개 위치·460개 후보이며 바이트 그대로 유지했다. 새 파일은 기존 로더와 후보 검증 함수를 통과했지만 **활성 설치하지 않았다**. [연결 검증 요약](pipeline-summary.json).

분기 비교의 검사 엔진 7개와 추가 재연구 엔진 1개는 모두 종료 코드 0을 확인했다. 기존 활성 기억의 전후 SHA256은 다음과 같다.

```text
c00cef2484dac5e90ae4eaa851f5f1cb82850d51881a2be5eacfd4ec66babcfa
```

분기 비교 뒤에 교육 자료의 추가 `reserved_holdout_position_keys`를 학습 도구까지 전달하는 작은 보존 수정을 더했다. 이 최종 변경은 별도 회귀 검사와 위 실제 연결 검증으로 확인했다. 전체 분기 비교를 다시 실행하지 않았으며, 두 실행 시점의 소스 스냅샷과 해시를 각각 보존했다.
