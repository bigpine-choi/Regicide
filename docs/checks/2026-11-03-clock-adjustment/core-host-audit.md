# 시계 조절 코어·호스트 독립 점검

2026-11-03. 임시 대국 폴더, 가상 시계와 통제된 엔진 응답만 사용했다. 실제 사용자 기보는 수정하지 않았다.

- 최종 관련 검사 68개 통과, 실패·오류·건너뜀 0개. `core-host.log`에 개별 결과, `core-host-summary.json`에 검사 대상과 실행 전후 SHA-256을 기록했다. 검사 중 대상 소스는 변하지 않았다.
- 코어 22개, 호스트 조절·동시성 13개, 기존 기본 시계 11개, 기존 사용자 시간 초과 정책 7개, 시계 보관함 15개를 실행했다.
- 1,000회 시간 조절을 양쪽 사용자 색상과 40개의 합법 착수에 분산했다. 소수점 경과 시간, 사용자 시간 소진 후 재충전, 증가 시간, 24시간 상한을 섞고 매 착수마다 독립적으로 잔액을 재계산했다. JSON 보관함과 PGN으로도 재생했다.

시간 조절은 실행 시점 하나를 기준으로 경과 시간을 먼저 정산하고, 선택한 시계에만 증감을 적용한다. 착수·증가 시간·보드 리비전은 만들지 않는다. 별도 `edit_revision`으로 이전 버튼 요청과 동시에 들어온 요청을 거부한다. 이미 패배한 엔진 시계는 되살릴 수 없고, 사용자 0초는 계속 대국할 수 있다. 아직 차례가 아닌 엔진의 0초는 다음 차례가 시작될 때 판정한다.

조절 기록에는 당시 보드 ply, 해당 차례에서 이미 쓴 시간, 선택한 색상, 요청 증감, 실제 증감, 전후 잔액과 리비전이 남는다. 기존 착수 완료 시각의 `%clk`는 다시 쓰지 않는다. 무르기는 남겨 둔 착수 완료 시점으로 복구하므로 그 ply에서 시작된 다음 차례의 조절은 버리고, 그보다 앞선 조절만 유지한다. 무르기 자체도 조절 리비전을 올린다. 편집 필드가 없는 기존 v1 기보와 과거의 미판정 0초 스냅샷도 읽을 수 있다.

호스트 독립 검사에서 진행 중 대기 시간을 늘리거나 줄여도 같은 수가 한 번만 적용됨을 확인했다. 탐색 중 새 목표에 따라 중단을 요청하고, 0초 조절 뒤 늦은 수가 도착해도 적용하지 않는다. 남은 시간 200ms 상태에서 1분을 추가한 뒤 원래 만료 시점보다 긴 실제 300ms를 기다려도 기존 타이머 때문에 엔진이 종료되지 않음을 확인했다. 핸디캡 미리보기·취소에서 원래 조절 기록도 보존된다.

호스트 검토에서 남은 차단 결함은 발견하지 못했다. 이 결과는 시계 계산·상태·저장·동시성의 검증이며, 실제 엔진 기력이나 GUI 수동 조작 결과를 뜻하지 않는다.
