# 실제 국면 재현과 자체 후보 탐색

2026-11-03, 실제 실행되는 Regicide 바이너리와 저장된 전체 착수 이력으로 확인했다.
정정 후 결과는 `activity-enabled/`에만 있다. 처음 폴더 바로 아래에 저장한 결과는
`UsePieceActivity=false`인 대조군이다. 실제 게임은 이 옵션을 **true**로 설정한다.
자세한 정정 경위는 `CORRECTION.md`에 기록했다. 대조군을 제품 동작의 증거로 쓰지 않는다.

조건은 Regicide Hash16, UsePieceActivity=true, 나머지 UCI 기본값이다.
Stockfish18은 Threads1, Hash32, 제한 강도 해제이며, 각 국면을 독립적으로 200,000노드
검색했다. 원본 게임, 전체 이력, 바이너리 해시, 원시 점수·완료 깊이·PV·실제 시간은
각 JSON과 manifest에 있다. 모든 점수는 원래 착수할 쪽 기준 cp이며 100cp=1폰이다.

|원래 문제 수|자체 검색 6초의 실제 완료 결과|Stockfish 원래 수를 둔 뒤|자체 생성 대안과 Stockfish 평가|
|---|---|---:|---|
|50.Ne5|Ne5, 깊이8, +123|-331|b4: 0|
|43...Bxc3|Bxc3, 깊이7, +140|-146|Rh1: +35|
|15...axb4|axb4, 깊이6, -23|-179|e6: -37|
|21...Nxe4|d5, 깊이7, +61|-174|d5: +87|
|27.Qxb7|Qxb7, 깊이7, +15|0|e6: +265|
|9.Nxa7|Qc4, 깊이6, +4|-433|Qc4: -57; e4: +17|

21...Nxe4는 원래 완료 깊이5를 고정하면 +21로 재현된다. 새 2.5초 검색은 이미 d5를
찾기도 하므로 동일 시간만으로 같은 오답이 항상 반복된다고 주장할 수 없다.
9.Nxa7는 1초/3초에서 깊이5 +17로 재현되지만 6초에서 Qc4로 바뀐다.
반면 50.Ne5, 43...Bxc3, 27.Qxb7는 검색 시간을 늘려도 위 한도 내에서 남았다.
15...axb4는 약7.9초에 깊이7을 마쳐 e6로 바뀌었다. 깊이 제한과 8초 제한을 함께
쓴 검색은 목표 깊이가 아니라 JSON에 기록된 실제 완료 깊이만 근거로 삼는다.

`repair_schedule.py`는 문제 수 및 직전 반환 후보를 차례로 제외하고
400/400/2500/500ms의 자체 탐색을 실행한다. Stockfish가 제안한 수를 후보에 넣지 않는다.
이 일정에서 실제 생성된 안전 후보는 각각 b4(깊이6), Rh1(5), e6(4), d5(4), e6(5),
Qc4(4)였다. 각 후보의 별도 Stockfish 자식 국면 평가도 함께 저장했다.
`native_alternatives.py`는 비교용 900ms 제외 탐색이며, `verify_shallow.py`는 이미
자체 생성된 얕은 후보만 400/900ms 단일 후보 검색으로 재확인한 추가 실험이다.

재실행: `.venv-tests/Scripts/python.exe docs/checks/2026-11-03-sparring-disagreement/probes/reproduce.py`
및 같은 폴더의 `repair_schedule.py`. 이들은 진단 산출물을 갱신하므로 기존 결과를
보존하려면 먼저 별도로 복사한다. 최종 필터 통합 검증은 별도
`tests/sparring_quality_native_integration.py`와 상위 폴더의 `guard-replay.json`을 따른다.

이 결과는 특정 국면의 평가 불일치와 후보 확보 가능성을 보여 준다. 전체 경기력,
Elo, 모든 기물 헌납 방지, 일반적인 대국 체감 또는 항상 접전 유지의 증명은 아니다.

## 초기 6국면 필터 통합 확인 (v1)

`guard-replay-v1.json`의 실행은 6/6 통과했고 실행 전후 소스와 양쪽 바이너리 해시가
같았다. 원래 문제 수를 고정 입력하고 실제 자체 엔진이 만든 대안만 최종 선택했다.
선택이 끝난 뒤 별도 새 Stockfish 프로세스로 원래 위치, 원래 수 이후, 최종 수 이후를
각각 3초 분석했다. 따라서 아래 점수는 위의 200,000노드 진단과 다른 실험이다.

|문제 수 → 실제 자체 대안|원래 수 이후 → 대안 이후 (원래 쪽 cp)|필터 시간|
|---|---:|---:|
|50.Ne5 → b4|-394 → 0|2.59초|
|43...Bxc3 → Rh1|-206 → +49|7.83초|
|15...axb4 → e6|-172 → -24|2.59초|
|21...Nxe4 → d5|-154 → +71|3.63초|
|27.Qxb7 → e6|0 → +302|2.64초|
|9.Nxa7 → Qc4|-451 → -80|2.60초|

최종 자체 후보의 완료 깊이는 순서대로 6, 5, 5, 4, 5, 4였다. 문제 수가 아닌 일반
착수 전체의 평균 시간은 이 실험으로 측정하지 않았다. 처음 심판을 켜는 시간은
약0.9초, 첫 검사는 약1.5초였고 같은 턴의 후속 검사에서 심판 프로세스를 재사용했다.

실패한 선행 실행도 숨기지 않고 상위 폴더에 보존했다. `guard-replay-startup-timeout.json`은
650ms 안에 심판 시작을 마치지 못한 0/6 실행이다. `guard-replay-cache-incomplete.json`은
완료된 정확 평가와 미완료 다음 반복의 반환 수가 달라 2건을 놓친 4/6 실행이다.
`activity-enabled/referee-incomplete.json`은 후자의 원시 패킷을 재현했다. 최종 구현은
완료된 위치 평가를 명시적으로 사용하며, 미완료 반환 수를 정확 평가한 것처럼 표시하지 않는다.

정책 단위 검증은 `tests/sparring_quality_policy_tests.py` 15건을 통과했다.
전체 GUI·대국 흐름과 장기 경기력은 이 통합 실행의 범위에 포함하지 않았다.

## 새 실제 대국에서 발견한 3국면 추가 (v2)

초기 6국면 통과 뒤 실제 대국에서 17.f4, 20.Nge4, 21.axb4 문제가 추가로 드러났다.
원본은 `docs/matches/2026-11-03-sparring-quality/1700-white/game.json`이다.
얕은 자체 후보를 바로 버리는 문제와, 안전 하한을 조금 넘겼다는 이유로 훨씬 나쁜
원래 수를 그대로 두는 문제가 있었다. 또한 전체 후보 순위 탐색만으로는 17.Nd5를
찾지 못했다. 기물 출발칸별 합법 수 묶음에서 자체 엔진을 검색하면 Nd5를 생성했다.
이 묶음은 보드에서 결정하며 Stockfish 추천 수를 강제로 넣지 않는다.

수정 뒤 기존 6개와 추가 3개를 합친 `guard-replay-v2.json` 결과는 **엄격 통과 8개,
명시적 손실 완화 1개**다. 전후 소스·바이너리 해시는 같았고 9개 모두 자체 후보로
교체됐다. 더 긴 독립 Stockfish 3초 검사에서는 9개 모두 그 검사의 허용 하한을
충족했다. 그러나 실행 중 짧은 검사에서 하한을 넘긴 한 건을 엄격 통과로 바꾸지 않았다.

|추가 문제 수 → 실제 자체 대안|독립 3초 평가: 원래 수 이후 → 대안 이후|실행 중 분류|필터 시간|
|---|---:|---|---:|
|17.f4 → Nd5|-264 → 0|엄격 통과|4.59초|
|20.Nge4 → Nxf7|-241 → -175|엄격 통과|2.53초|
|21.axb4 → Nxf6|-719 → -234|손실 완화|7.83초|

21수의 짧은 검사는 원래 수 -630cp, Nxf6 -158cp였다. 당시 하한 -136cp와 오차
20cp를 적용하면 2cp 차이로 하한을 충족하지 못한다. 그래서 안전하다고 표시하는
대신 472cp 손실 완화로 기록했다. 별도 3초 검사는 원래 위치 -257cp, Nxf6 이후
-234cp였다. 이미 불리한 국면을 접전으로 되돌렸다는 뜻은 아니다.

통합 검사기는 이 구분을 유지하여 `strict_pass_count=8`, `mitigation_improvement_count=1`,
`passed=false`를 기록하고 종료 코드 1을 반환한다. 실행 오류를 숨기거나 손실 완화를
엄격 성공으로 합산하지 않았다. 후보 생성·승격·검색 시간 실험은 `quality-*.json`에
보존했다. 20수 국면은 짧은 루트 검사 -45cp와 500ms 검사 -140cp가 크게 달랐으므로,
완료 깊이와 정확 점수 형식만으로 평가가 수렴했다고 주장할 수 없다.
