# 갬빗 탐색 시간 확대와 반복 체크 진단

2026-11-04 진단 기록. **시간제 갬빗 모드가 기존 착수 목표 안에서 실제 탐색에 더 많은 시간을 쓰도록 수정했다.** 아래 일곱 C++ 후보는 채택하지 않았고 활성 실행 파일이나 무승부 점수를 변경하지 않았다. PGN의 `DrawPolicy` 설명도 현재 대국 규칙과 일치시켰다. **문제 국면의 반복 체크 오판은 아직 해결되지 않았다.** 탐색 깊이 증가와 수 선택의 개선을 구분한다.

## 채택한 시간 배분 변경

`engine_pacing.search_budget(..., deepen=True)`를 시간제 갬빗 모드에서만 요청한다. 기존 기본 탐색은 보통 전체 탐색 허용량의 1/3, 최대 3초였다. 새 방식은 남은 표시 시간에서 후보 검증 예산, 완료 여유, 시계 보존분을 제외한 부분을 기본 탐색에 추가한다. 착수 목표를 새로 늘리거나 이미 경과한 시간을 다시 배정하지 않는다. 기존 1.5초 표시 시간 단축도 보존한다. 명백한 응수, 익숙한 개시, 남은 시계 10초 이하, 수동 연구 설정, 기본·스파링 모드는 기존 경로다.

기존 공통 시간 정책 v13은 유지하고, 추가 배분이 실제 발생한 수에만 `regicide-gambit-search-time-v1`과 이전 예산·추가 예산을 기록한다. 엔진에 넘기는 실제 검색 시간을 늘린 것이며 깊이·평가 숫자를 보정하지 않는다. 갬빗 희생 검증을 위한 별도 예약도 유지한다.

| 선언된 개발 국면 | 기존 / 새 탐색 요청 | 기존 / 새 완료 깊이 | 선택 |
| --- | --- | --- | --- |
| 아래 반복 체크 위험 위치 | 3,000 / 14,736ms | 7 / 9 | `...a3` 유지, 오판 미해결 |
| Kiwipete | 3,000 / 13,324ms | 5 / 6 | `dxe6` 유지 |
| 룩 엔드게임 | 3,000 / 11,629ms | 9 / 10 | `Rc4` 유지 |

이 비교는 같은 계획상 착수 시간에서 대기를 실제 계산으로 바꾼 비교다. **동일 CPU 시간 비교가 아니다.** 새 Kiwipete 검색은 요청 상한을 모두 사용하지 않고 일찍 종료했으므로, 요청 시간을 실제 소비 시간으로 해석하지 않는다. 실행 파일·옵션·원시 패킷·소스 해시·순차 실행 순서는 [실제 깊이 검증](deeper-search-validation.json), 실행 도구는 [gambit_depth_validation.py](../../../tests/gambit_depth_validation.py)에 남겼다. 세 국면은 개발 표본이며 Elo·전체 경기력 평가가 아니다.

제어된 시계와 실제 Host 코드 경로에서는 전체 표시 턴 약 4.65초를 유지하면서 기본 탐색 요청이 2.0초에서 4.5초로 증가했다. 이는 가짜 엔진을 쓴 배분 검증이며 실제 엔진 결과는 위 표와 분리한다. 신규 13개 검사, 관련 기존 78개 회귀, PGN·반복 경계 3개 검사가 통과했다.

별도의 [실제 Host 실행](deeper-search-host-smoke.json)에서는 자체 엔진에 14.734초를 전달했고 약 14.899초에 합법적인 `...a3`를 적용했다. 임시 저장 폴더만 사용했으며 모든 실행 프로세스가 정상 종료했다. 실행한 검증 도구와 변경 소스의 원본 바이트는 `validation-sources.zip`에 보존했다. 앱이 이미 실행 중이었다면 새 시간 배분 코드를 사용하려면 다시 실행해야 한다.

개인 대국의 전체 기보·게임 식별자·원본 파일은 이 폴더에 포함하지 않는다. 아래 최소 FEN과 짧은 변화만 공개한다. 실제 대국에서 이미 발생한 반복의 권리를 확인할 때에는 FEN 하나가 아니라 해당 위치까지의 이력이 필요하다.

## 재현한 문제

흑 차례의 최소 시작 위치다.

```text
r4k2/2p5/1pqp4/5r2/p3R2R/2B3P1/PP3P1P/6K1 b - - 3 31
```

활성 Regicide SHA256은 `5011da4c5e6ef01c452bd7125e4e22b372d2c9cfb858ed8759057325acb0e6ba`다. 실제 앱과 같이 `UsePieceActivity=True`를 적용하고 다른 옵션은 기본값으로 두었다. UCI에 2085ms를 요청했으며 기본 Move Overhead 20ms가 적용된다. 이 환경의 단일 시간제 실행으로, CPU 격리나 일반적인 속도·기력 비교는 아니다.

원본 이력을 유지한 별도 비공개 재현과 위 FEN만 사용한 공개 재현 모두 `31...a3`, 흑 기준 **+441cp·완료 깊이 7**을 반환했다. 대표 자체 수순은 다음과 같다.

```text
31...a3 32.Rh8+ Kf7 33.Rh7+ Kf8 34.Ree7 axb2 35.Bxb2
```

현재 탐색은 상대가 체크를 계속할 가능성을 충분히 반영하지 못하고, 상대가 체크를 멈추는 수순을 우세로 읽었다. 제한 수 검색에서 `...a3`만 허용해도 완료 깊이 9까지 +441cp가 유지됐으므로, 이 사례는 단순히 깊이 숫자를 한 단계 늘려 해결된 문제가 아니다.

별도 Stockfish 18 사후 감사에서는 같은 시작 위치의 `...a3`, `...Qc5`, `...d5`가 무승부 평가였고, `...Re5`·`...Qxe4`에는 흑 기준 약 +2.1~+2.4의 우세가 남았다. Stockfish의 제한 깊이 평가도 수학적인 승리 증명은 아니다. 조건·원시 결과는 [사후 감사](stockfish-audit.json)에 구분한다. 외부 수나 점수를 자체 엔진의 실제 착수 선택에 넣지 않았다.

## 마지막 반복 수를 억지로 피하면 안 되는 이유

위 시작판에서 다음 수순을 재생하면 이후의 체크 국면을 최소 이력으로 구성할 수 있다.

```text
a4a3 h4h8 f8f7 h8h7 f7f8 h7h8 f8f7 h8h7
```

이후 흑 차례의 위치는 다음과 같다.

```text
r7/2p2k1R/1pqp4/5r2/4R3/p1B3P1/PP3P1P/6K1 b - - 7 35
```

이 시점의 사후 감사에서는 `...Kf8`·`...Kg8`가 0이고 `...Kg6`는 흑에게 불리했다. 따라서 마지막의 무승부 선택을 금지하면 오히려 패배하는 수를 강요할 수 있다. 문제는 앞선 `...a3`로 지속 체크를 허용한 판단이다. 기물 가치가 500cp 앞선다는 사실과 실제로 승리를 유지할 수 있다는 판단은 구분해야 한다.

C++ 코드는 현재 3회 반복·50수 청구를 선택 가능한 0점으로, 5회 반복·75수 조건을 자동 무승부로 구분한다. 메이트 판정은 카운터보다 우선한다. 이 값들을 가짜 음수로 바꾸거나 합법적인 무승부 권리를 삭제하는 변경은 하지 않았다.

## 격리한 일곱 후보: 모두 미채택

공유 `src/`를 바꾸지 않고 별도 소스와 바이너리로 실행했다. 표의 숫자는 각 후보의 자체 평가이며 외부 판정이나 실제 승률이 아니다. 시간제 비교는 원칙적으로 같은 2085ms 요청, classical 활동성 평가다. 깊이 1 제한 검색은 별도 행으로 설명한다.

| 후보 | 실제 선택 | 자체 평가·완료 깊이 | 불채택 근거 |
| --- | --- | --- | --- |
| 안정화 탐색의 조용한 체크 예산 2 | `...a3` | +441cp·7 | 같은 오판 유지 |
| 조용한 체크 예산 3 | `...a3` | +441cp·6 | 같은 오판을 유지하며 완료 깊이 감소 |
| 조용한 체크 예산 6 | `...d5` | +428cp·3 | 선택은 달라졌지만 외부 감사에서 이 수도 무승부 |
| 현재 검색 경로 안의 첫 재방문을 0으로 추정 | `...Qc5` | +432cp·7 | 외부 감사에서 이 수도 무승부 |
| 검색 경로 재방문 추정 + 체크 예산 3 | `...d5` | +428cp·5 | 외부 감사에서 이 수도 무승부 |
| 체크 예산 32 + 별도 안정화 탐색 캐시 | `...a3` 대체 수 | **완료 깊이 0** | 깊이 1도 완료하지 못함. 평가로 사용할 수 없음 |
| 정규 탐색의 체크 회피 확장, 경로당 최대 2회 | `...a3` | +441cp·6 | 같은 시간과 같은 노드 수 모두에서 오판 유지 |

체크 예산 6 후보에서 `...a3`만 허용한 별도 깊이 1 검색은 약 43.5ms·15,642노드에 완료됐지만 여전히 +441cp였다. 체크 예산 32와 캐시를 함께 켠 후보는 같은 제한 수·깊이 1 조건에서 약 11.7ms·2,953노드 뒤 안정화 탐색의 절대 깊이 상한에 도달했다. 체크가 해결되지 않은 경계에서 기존 `Interrupted`가 첫 반복 전체를 취소한 경로와 일치한다. 출력된 +451cp는 **미탐색 루트 대체 수의 정적 참고값**이며, 완료된 후보 평가가 아니다. 자유 루트 시간제 검색은 이 마지막 후보에서 추가 실행하지 않았다.

검색 경로 재방문 후보는 정식 무승부 판정을 추가한 것이 아니다. 검색 시작 뒤 방문한 정확한 반복 위치가 다시 나타나면 0을 추정하는 실험이었다. 이전 개인 기보의 두 번째 출현만으로 자르지 않는다. 제한된 루트 수 집합에서 시작한 위치와 제한 없는 후손의 의미가 다를 수 있는 등 별도 경계도 남아 있으므로 일반 기능으로 사용하지 않는다.

조용한 체크 예산은 전체 안정화 탐색 경로에서 공유되는 상한이다. 연속 체크만 특별히 확장한 정책은 아니며, 예산을 늘리면 탐색량과 완료 깊이가 함께 달라진다. 숫자를 계속 늘리는 방식의 추가 튜닝은 이 단계에서 중단했다.

### 후속 정규 탐색 체크 회피 확장

마지막 후보는 조용한 체크 예산을 늘린 것이 아니다. 기존 안정화 탐색의 체크 예산 1은 유지하고, 정규 탐색의 진입 위치가 체크일 때 남은 경로 예산을 하나 써 탐색 깊이를 1 늘렸다. 최초 예산은 2이며 PVS·LMR의 다섯 재귀 호출에 같은 남은 예산을 전달했다. `ply + depth < 64`일 때만 확장하고, 실험용 전이표 키에 남은 예산을 구분했다. 검색 경로 재방문 0점 추정은 결합하지 않았다.

같은 FEN·활동성 평가·2085ms 요청에서 여전히 `...a3` +441cp, 명목 완료 깊이 6을 반환했다. 이어서 활성 기준과 후보에 **각각 정확히 850,000노드**를 요청했다.

| 같은 노드 수 비교 | 총 방문 노드 | 마지막 완료 깊이 | 실제 선택·자체 평가 | 완료 반복을 처음 발표한 시점의 누적 노드 |
| --- | ---: | ---: | --- | ---: |
| 활성 기준 | 850,000 | 7 | `...a3`, +441cp | 476,161 |
| 체크 회피 확장 후보 | 850,000 | 6 | `...a3`, +441cp | 289,662 |

마지막 열은 전체 계산량이 아니다. 다음 반복을 시도하다 중단된 작업까지 포함한 최종 총 방문 수는 양쪽 모두 850,000이다. 완료 패킷에 처음 실린 누적 노드 수와 최종 총 카운터를 별도 필드로 보존했다. 후보의 시간제 실행 총 노드는 854,493이며, 해당 실행의 마지막 완료 반복 발표 시점도 289,662노드였다. 이 명목 깊이는 연장된 선택적 탐색을 포함하므로 두 정책의 깊이 숫자 자체를 기력 비교로 해석하지 않는다.

실행 중 실제 앱도 열려 있었으므로 벽시간을 통제한 비용 비교로 사용하지 않는다. 정해진 시간 안의 선택과 같은 노드 수의 선택 모두 이 개발 위치에서 개선을 보이지 않았다. 후보는 채택하지 않았고 별도 여섯 국면의 확대 검증도 진행하지 않았다. 소스·컴파일 명령·두 후보 실행·동일 노드 기준 실행은 [checked-node-extension.zip](checked-node-extension.zip)에 보존했다. 압축 안의 원본 해시 manifest와 모든 저장 바이트의 재검사를 통과했으며, 처음 여섯 후보의 `experiments.zip`은 수정하지 않았다. 새 압축 파일 SHA256은 `42e33f2fa8e4468e31bf07b13e79c2502013503c0a2a6e19a6d8e66fdb2213d6`이다.

## 보존과 검증 범위

[experiments.zip](experiments.zip)에는 여섯 격리 후보의 C++ 소스·필요한 헤더·컴파일 명령·기록용 manifest·공개 검색 결과를 보존했다. 실행 파일과 객체 파일, 개인 전체 기보, 비공개 전체 이력 재현 자료는 제외했다.

- 압축 파일 SHA256: `5b05d015a809d19e9bb2d3bbcfe643d5447f9c501957f81cf39e18c142e7738d`.
- 압축 안의 `archive-manifest.json`은 27개 자료의 원본·보관 바이트 수와 SHA256을 기록한다. 26개는 원본 바이트를 그대로 보존했고, 한 결과는 개인 이력 관련 표식을 제외한 공개 투영본으로 별도 원본·보관 해시를 기록했다.
- 압축을 다시 열어 모든 보관 해시, 원본 보존 자료의 원본 해시, 압축 무결성과 파일 목록을 확인했다. 공개 자료에 개인 게임 ID나 전체 기보가 포함되지 않는지도 검사했다.
- 검색 중에 자체 평가가 호출됐다는 사실이나 한 위치의 선택 변화는 경기력 향상의 증거가 아니다. 이번 일곱 후보는 실전 정책과 활성 엔진에 반영하지 않았다.

공개 대조 국면의 실제 엔진 검증은 [public-validation.json](public-validation.json)에 별도 기록한다. 현재 실행 파일로 9개 국면의 완료된 합법 PV, 정상 종료, 이력 보존을 확인했다. 뒤늦게 형성된 반복 국면에서는 0점 자원을 인식했고, 독립적인 메이트 1수 국면에서는 반복 청구보다 메이트를 골랐다. 앞선 `...a3`의 오판은 그대로 재현됐다.

다음 엔진 개선에서는 `...Kg6` 뒤의 `Rg7+`, `Re6+`, `g4+` 등 구체적인 반박을 어느 경계에서 놓치는지 먼저 좁혀야 한다. 평가기 오판, 선택적 탐색, 반복 체크에 쓰는 비용을 분리하고, 새 구현은 이 개발 위치와 다른 공개 대조군에서 같은 시간으로 확인해야 한다. 현재 결과로 엔진의 전체 경기력·Elo 향상이나 문제 해결을 선언하지 않는다.
