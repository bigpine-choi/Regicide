# CPU 중단 해석 재검토

2026-10-21 KST. **사용자가 다른 앱을 열었다는 증거는 없다. ‘다른 앱의 부하 때문에 중단했다’는 설명을 정정한다.** 실제 확인한 것은 기존 감시기가 계산한 잔여 CPU 지표의 상한 초과다. 현재 백그라운드 서비스 부하와 감시 방식의 한계를 추가로 관측했으며, 이를 과거 중단 원인으로 소급 단정하지 않는다.

## 지표의 실제 의미

기존 값은 `Windows 전체 busy CPU − 관측하여 소유를 확인한 worker 계열 CPU`다. 전체 논리 CPU 시간 대비 비율이다. 감시기·대국 관리·파일 검증 프로그램, OS 작업, 접근하지 못한 서비스, 관측 사이에 생성·종료된 실험 자식과 비동기 측정 오차도 잔여에 섞일 수 있다. 프로그램 창을 열었는지를 측정하는 값이 아니다.

GetSystemTimes의 kernel에 idle이 포함되는 점과16논리 CPU의 합산은 현재 코드에 맞게 처리됐다. 등록한 프로세스의 Python·엔진 스레드는 프로세스 CPU에 포함된다. 그러나 산술 일치가 특정 앱의 책임을 입증하지는 않는다.20%/2초는 이번에 고정한 환경 문턱이며 개별100ms 탐색의 실제 경합이나 기력 손실을 직접 증명하는 값도 아니다. [원리 감사](README.md), [독립 검토](review.md)를 따른다.

## 현재의 실제 관측

1. [24초 읽기 전용 native 관측](current-host-001/receipt.json)에서 전체 CPU는 약9.0~18.0%였다. 프로세스별 합계는 전체보다 작았고 보호된 서비스의 개별 CPU를 읽지 못했다.
2. 이를 보완한 [WMI raw counter 관측](current-cim-001/receipt.json)의 앞5구간에서 `mc-fw-host` PID7324가 전체 논리 CPU 대비 약8.4~16.1%를 사용했다. 같은 구간의 native 전체 CPU는 약21.9~27.8%였다. [서비스 조회](service-identity.json)에서 표시 이름 **McAfee Framework Host**, 상태 Running을 확인했다. 일반 앱 창이 없어도 서비스는 실행될 수 있다.
3. 이 관측에는 진단 프로그램과 WMI의 부하도 포함한다. 마지막6번째 구간에는 별도 자체 CPU 교정 작업이 겹쳤으므로 평상시 배경 부하 수치로 사용하지 않는다. WMI와 native 읽기 구간은 완전히 동시에 일치하지 않는다. 진단 활동이 서비스 부하를 유발했는지도 이 자료만으로 확정할 수 없다.
4. 이전 Teams WebView 급증도 당시의 제한된 관측이다. Teams 또는 McAfee가 과거004/005 중단을 일으켰다고 확정하지 않는다.

WMI 수식·필드는 [Microsoft의 raw process counter 문서](https://learn.microsoft.com/en-us/previous-versions/aa394323(v=vs.85)), [두 표본을 이용하는 성능 관측 설명](https://learn.microsoft.com/en-us/windows/win32/wmisdk/wmi-tasks--performance-monitoring)을 확인했다. 명령줄·환경·프로세스 메모리·창 내용은 수집하지 않았다.

## 감시기 자체의 CPU 차감 교정

실제 체스 대국 대신 직접 생성한 Python 작업만 실행하고 Windows Job의 누적 CPU와 기존 감시기의 차감치를 비교했다. [실행 원문과 설명](native-job-probe/README.md)을 따른다.

- 오래 실행한4개 root의 CPU는 Job 누적 CPU·감시기 차감·최종 프로세스 CPU 합계가 정확히 일치했다.
- 짧은 자식32개가 모두0.5초 간격 표본 사이에 생겼다가 종료되는 별도 사례에서는 감시기가 이들을 관측하지 못했다. workload 구간의 Job CPU7.609375초 중 감시기 차감은0.40625초였다. Job 기준 차이는7.203125 CPU초다.
- 직접 보유한 자식 핸들의 최종 CPU 합은7.25초였다. 전체 root+자식 합과 Job 누적치 사이에도0.046875초의 잔차가 있어 정확한 가산 일치를 주장하지 않는다. 할당 경계·계수 정밀도 등의 원인은 미확정이다.
- 두 번째는 **귀속 교정 전용 실험**이다. 원래20% 검사 실패는 그대로 보존했고, 추가 교정에서만100% 진단 상한으로 관측을 계속했다. `formal_load_validation=false`, `valid_for_formal_comparison=false`, 원래20% 기준이라면 실패한다는 표기를 명시했다. 정식 대국의 부하 검사를 통과했다는 뜻이 아니다.

이 사례는 자체 실험의 CPU도 잔여로 셀 수 있음을 재현했다. 실제004/005 중단 직전의 관측된 worker 구성은 안정적이었으므로, 교정 사례가 과거 중단 원인이었다고 단정하지 않는다. 과거 자료로는 관측하지 못한 작업까지 복원할 수 없다.

## 유지하는 판정과 다음 측정 원칙

004의 본176판과005의 사전12판은 원래 계획상 무효 상태를 유지한다. 사용자가 다른 앱을 켰다는 설명이나 앱을 닫으면 해결된다는 결론은 철회한다. 후속 실험에서는 Job의 누적 CPU, 감시·관리 자체의 CPU, 접근 가능한 시스템 서비스별 부하를 분리하고 관측 오차를 기록한 뒤 환경 기준을 정해야 한다. 기존 엔진·M2 감시 코드·계획의 수치와 실패 원문은 이번에 바꾸지 않았다. 서비스·앱·보안 설정을 조작하지 않았으며 진단에서 직접 만든 작업만 종료했다.
