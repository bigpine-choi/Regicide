# 스파링 모드: 맞춤 연습과 후반 강도 상승

2026-11-02. `regicide-sparring-play-v1`은 상대가 실제로 둔 수의 탐색 손실을 관찰해 작은 양보를 선택하는 별도 연습 모드다. 일반 모드와 갬빗 보스의 수 선택 정책을 바꾸지 않는다. 50수가 지난 뒤 양보를 줄여 승리를 노리지만, 접전 유지·승리·특정 Elo를 보장하지 않는다.

## 현재 동작

먼저 설정된 생각시간 전체를 사용해 Regicide의 기준 최선수를 구한다. 직전 인간수의 손실은 그 수를 두기 전의 같은 위치에서 최선수 탐색과 실제 수로 제한한 탐색을 비교한다. 같은 완료 깊이의 정확한 점수와 합법적인 예상 수순이 있을 때만 관측으로 인정한다. 강제수, 불완전한 탐색, 잘못된 이력, 중복 관측은 실력 근거로 누적하지 않는다. 되돌리기 후에는 남아 있는 실제 기보에서 관측을 다시 구성한다.

유효 관측 3개 전에는 내부적으로 파악 단계로 두고 양보하지 않는다. 대국 화면에는 스파링 모드라는 이름만 표시하며 내부 단계·관측수·양보 목표는 기록에 남긴다. 이후 최근 12개 관측에 더 큰 가중치를 두고 사전값과 결합하며, 한 번의 관측으로 평활 손실 추정치가 변하는 폭을 최대 12cp로 제한한다. cp는 엔진 평가에서 폰 하나를 약 100으로 두는 단위다. 이 값은 현재 대국의 휴리스틱 지표이며, 공인 실력이나 정확한 승률 추정치가 아니다.

양보 목표는 최대 90cp이며 형세와 진행 단계에 따라 더 줄어든다. 후보는 자체 엔진의 얕은 탐색으로 찾은 뒤 기준 최선수와 **같은 완료 깊이**에서 다시 검증한다. 얕은 발견 점수만으로 착수하지 않는다. 불리한 형세에서는 양보를 줄이고, 우세한 형세에서는 평가 하한을 지킨다. 평가가 불안정하거나 메이트가 보이는 경우, 체크·반복 국면, 사용자 강제수 대국, 시간 초과, 적절한 후보가 없는 경우에는 기준 최선수를 유지한다. 제한된 탐색이 놓치는 전술까지 안전하다는 뜻은 아니다.

후보를 둔 뒤 상대의 한 번의 합법 포획과 즉시 재포획을 확인해 명백한 큰 기물 헌납을 걸러낸다. 목표 손실과의 차이가 비슷한 검증 후보들 사이에서는 전개와 위협을 선호한다. 강도를 높이는 구간에는 상대의 합법 수와 왕의 이동 칸을 줄이는 좁은 보조 기준의 비중을 높인다. 체크만으로 응수가 줄어든 경우에는 압박 가산점을 주지 않는다. 이는 자연스러운 인간 수나 ‘아나콘다’ 같은 경기 스타일을 입증하는 모델은 아니다. 평가 게이지의 실제 탐색 점수를 접전처럼 보이게 조작하지 않는다.

## 50수 이후의 일정과 시간

여기서 **50수는 백과 흑이 각각 50수를 둔 시점, 즉 완료된 100반수**다. 재료가 빨리 줄었다는 이유만으로 이 일정을 앞당기지는 않는다.

| 완료된 반수 | 운영 방식 |
| --- | --- |
| 0~99 | 관측 부족 시 파악, 이후 상대 관측과 형세에 맞춘 제한적 양보 |
| 100~139 | 약 20수에 걸쳐 양보 목표를 선형으로 줄임 |
| 140 이상 | 스파링 양보 없이 설정된 생각시간의 기준 최선수 사용 |

메이트·규칙상 무승부 등으로 대국이 50수 전에 끝날 수 있다. 후반 전력 전환은 반드시 이긴다는 뜻이 아니며, 낮은 생각시간을 사용하면 그 시간 제한도 그대로 남는다.

기본 생각시간은 보존하고, 그 외에 **최대 2000ms**의 보조 탐색 예산을 사용한다. 보조 예산은 `min(2000, 기본시간 × 2)`이며 상대 수 관측에도 같은 예산을 나눠 쓴다. 따라서 1000ms 설정이면 탐색 예산 합계는 최대 3000ms다. 통신·처리 시간까지 항상 정확히 3초라는 의미는 아니다. 기본시간이 **600ms 미만이면 자동 조절을 보류**하고 기준 최선수를 사용한다. 140반수부터는 이 보조 탐색을 하지 않는다.

## 검증 기록의 구분

정책 회귀 검사 `tests/sparring_play_tests.py` 17개가 통과했다. 관측의 완만한 변화, 정확한 상대와 실수가 잦은 상대의 선택 차이, 이력·되돌리기, 같은 깊이 검증, 메이트·기물 헌납 방지, 100~140반수 일정과 평가 하한을 포함한다. 이는 구현된 조건의 검사이며 실제 사람의 재미나 자연스러움을 측정한 검사는 아니다.

최종 안정성 기준은 **깊이 4 이상에서 최근 연속 2개 이상의 정확한 완료 기록**이다. 최대 최근 3개를 함께 확인하고, 기준수의 일치·점수 범위 80cp 이하·점수 관점·수순 합법성을 요구한다. 최신 기록의 경계값·오류·누락을 건너뛰어 안정적이라고 판정하지 않는다. 최신 기록만 경계값이면 범위 평가, 과거 기록만 경계값이면 잠정 평가로 구분한다. 이는 반복 탐색의 일관성 지표이며 평가 함수의 정확도나 승률 향상 측정은 아니다.

후보 발견은 깊이 3으로 실행한다. 초기 깊이 4 설정에서는 짧은 분할 예산 안에 후보가 완성되지 않는 문제가 실제 검사에서 드러났다. **발견 깊이와 최종 검증 깊이는 다르며**, 선택은 여전히 깊이 4 이상인 기준 탐색과 동일한 완료 깊이로 검증한다.

[최종 실제 엔진 통제 검사](policy-controls-v2.json)는 같은 합법 위치에 과거 관측만 다르게 넣었다. 과거 손실은 시험용 입력이며, 직전 인간수와 후보수의 평가는 실제 Regicide가 계산했다.

| 통제한 과거 관측 | 실제 선택 | 검증 결과 |
| --- | --- | --- |
| 정확한 상대 | 기준수 `c8e6` 유지 | 양보 목표 0 |
| 실수가 잦은 상대 | `c8e6` 대신 `c6a5` | 깊이 3으로 발견 후 깊이 5 재검증, 손실 32cp·목표 70cp, 보조 처리 약 610ms |

[실제 호스트 대국 검사](native-summary.json)는 100ms Regicide를 인간 역할의 대리 상대로 사용하고, 스파링은 기준 1000ms와 최대 2000ms 보조 예산을 사용했다. 표준 시작 위치에서 108반수(54수) 후 흑 스파링의 체크메이트로 정상 종료했고 [PGN](short-game.pgn)과 보관함 재생이 일치했다. 유효 상대 관측은 49개였다. **이 대국에서는 상대가 정확하다고 추정되어 양보 선택이 0회였으므로 접전 조절의 성공이나 50수 연출의 증거로 해석하지 않는다.** 대국 완료와 관측 누적의 기능 검사다. 별도로 기존 자체 대국의 99·100·120·140반수 위치에서 단계 전환을 확인했으며, 140반수에서는 보조 탐색 없이 기준수를 유지했다.

호스트 대국 검사 이후 수정한 부분은 후보 발견 깊이 4→3 및 과거 경계값의 표시 분류다. 대국에서 후보 발견 경로는 실행되지 않았고, 수정된 후보 경로는 위 최종 통제 검사로 확인했다. 각 결과의 `source_sha256`은 해당 실행 당시 소스를 구분한다. 2단계 실력 추정의 임계치나 양보 상한을 이 대국 결과로 보정하지 않았다.

격리한 실제 호스트 상태와 별도의 현재 위치 자체 엔진 평가를 [화면 입력](ui-fixture.json)으로 저장했다. `godot/tests/sparring_render.gd`로 1240×860·900×680 화면을 렌더하고 직접 확인했다. `rendered/manifest.json`의 실제 입력과 추가로 만든 상태 변형은 각각 `synthetic: false/true`로 구분된다. 이는 저장 상태를 이용한 화면 검증이며 수동 대국을 했다는 뜻은 아니다.

주요 검사: 정책 17개, 평가 안정성 18개, 호스트·HTTP·기보 연결 7개, Godot 모드 50개·게이지 56개·생각 시간 39개, 웹 모드/신뢰도 회귀 통과. 기존 일반·보스·기보·평가·힌트 검사도 통과했으며, 선택적인 실제 엔진 검사와 계정이 지원하지 않는 심볼릭 링크 검사는 각 로그의 생략 항목으로 구분한다.

재현 예:

```powershell

.venv-tests/Scripts/python.exe tests/evaluation_stability_tests.py

.venv-tests/Scripts/python.exe scripts/check_sparring.py --binary <Regicide.exe> --output <새 출력 폴더> --rounds 55 --opponent-ms 100

```

## 자체 구현과 외부 도구의 범위

착수 후보의 탐색·평가와 엔진 내부의 합법 수 처리는 자체 C++ Regicide가 수행한다. 스파링의 관측·후보 선택·일정·기록 정책은 프로젝트에서 작성한 Python 코드다. 기존 의존성인 `python-chess`는 호스트의 보드와 기보 재생, FEN·PGN, 합법성 교차 확인, UCI 통신 등에 사용한다. 외부 엔진의 점수나 착수를 스파링 선택에 섞지 않았다.

인간과 비슷한 수를 예측하는 문제는 단순히 승률이나 기력을 낮추는 문제와 다르다. Maia 원논문은 인간 행동을 개별 수 수준에서 모델링하는 목표와 전체 경기력의 일치를 구분한다. 이 점을 설계의 한계 설명에 참고했으며, Maia의 코드·학습 데이터·모델을 가져오거나 실행하지 않았다. [McIlroy-Young 외, *Aligning Superhuman AI with Human Behavior: Chess as a Model System* (2020)](https://arxiv.org/abs/2006.01855).

현재 검증한 것은 관측·제약·수 선택·단계 전환의 동작이다. 기력 수준, 승리 가능성, 50수 동안의 접전 유지, 사람이 느끼는 박진감과 자연스러움은 별도 대국 및 사용자 평가가 필요하다.
