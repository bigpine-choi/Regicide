## 실행과 품질 판정

- 기준과 후보를 각각 새 프로세스에서 자신의 동결된 source-root로 실행한다. 실제 `HumanGame.engine_move`가 수를 선택하며 특정 정답 수를 넣지 않는다.
- 같은 5011 자체 엔진·고전 활동성 평가·Hash16MiB, 기본 검색 1000ms와 기존 추가 상한 1000ms를 사용한다. NNUE·신경망·연속 체크 실험은 비활성이다. 표시 도우미는 검색하지 않는 객체다.
- 위치·seed별로 실행 순서를 교대한다. 선택·원본 이력·합법성·자체 엔진의 실제 반환·요청 시간 상한·정상 종료·소스 해시를 검사한다. 요청 시간 상한이 같아도 실제 CPU 사용량·경과 시간·완료 깊이가 같다고 가정하지 않는다. 영수증의 요청 상한 검사는 실제 벽시계 시간의 상한을 증명하지 않는다.
- 모든 자체 선택이 끝난 뒤에만 Stockfish18로 사후 감사한다. 같은 국면의 세 seed에서 나온 양쪽 실제 수를 합쳐 감사하므로 한 국면의 모든 seed는 같은 정확한 완료 깊이로 비교된다. SF18은 단일 스레드·Hash32MiB·최대 깊이18·각 검색 최대1초이며 실제 공통 완료 깊이를 기록한다.
- 창의성 제안 횟수, 실제 채택 횟수, seed별 고유 착수 수를 분리한다. 후단 안전 검증이 수를 바꾼 경우 `creativity.applied`만으로 실제 창의적 착수를 세지 않는다. 최종 수와 영수증이 일치하고 정산된 상대 응수 뒤 선택된 이름의 모티프가 실제로 양수여야 한다. 다양성 증가를 귀속할 때에는 기준의 세 seed에서 없었던 새 수 자체가 이 창의성 검증을 통과해 채택됐는지도 연결한다.

개발 표본 통과 조건은 기능·전체 감사 정상, 바뀐 착수에서 외부 손실 증가가 어느 경우에도 50cp를 넘지 않음, 바뀐 24쌍 부분집합의 손실 합이 기준 이하, 최소 한 국면에서 실제 고유 착수 수 증가, 최소 한 번의 응수 뒤 모티프 유지 선택이다. 시간 제한으로 자체 기본 수가 바뀐 것을 창의성으로 오인하지 않도록, 창의적 다양성 증가의 귀속에는 모든 seed·양쪽의 native 기본 수가 같은 국면도 최소 하나 요구한다. 변경 수에 메이트 점수가 나타나 일반 cp 비교가 불가능하면 그 결과로 통과를 선언하지 않는다.

이 기준은 소규모 개발 표본의 판정이다. 완주 대국·Elo·전역 기력 유지 또는 통계적으로 입증된 무퇴행을 뜻하지 않는다. 판정 후 코드나 조건을 바꾸면 이전 결과를 보존하고 새 실행으로 구분한다.

## 001: 첫 후보의 실제 결과

`host-ab-001/report.json`에서 고정한 24쌍의 실제 자체 선택 48회와 8국면의 사후 감사를 완료했다. 기능·소스·입력·하네스·바이너리 해시 검사가 통과했고 모든 소유 엔진은 정상 종료했다. 자체 선택을 모두 끝낸 뒤에만 SF18을 호출했다. [요약](comparison-001.json)에 원시 보고서 해시와 전체 판정·국면별 다양성을 보존했다.

실제 변경은 **0/24**, native 기본 수도 양쪽 24/24가 같았고 모든 국면의 고유 선택은 한 개였다. 따라서 같은 실행의 외부 손실도 양쪽 같았다. 품질·정상 실행 조건은 충족했지만, 실제 창의적 채택·응수 뒤 모티프 유지 선택·다양성 증가가 모두0이므로 사전 수용 조건은 **실패**했다. 이 결과를 창의성 개선으로 표현하지 않는다.

18개 입력이 창의성 후보 경로에 들어갔고 나머지6개는 기존 선택 보호 또는 비대상 경로였다. 시도별 거부는 `outside_zero_loss_floor`12개, 같은 깊이 검증 미완료2개, 새 기물 헌납 사전 검사19개였다. 사전 검사로 넘긴 후보도 세므로 이33개를 네이티브 검색33회로 세지 않는다. 실제 네이티브로 검증을 완료한 모티프 후보12개는 기준보다 자체 평가가20~108cp 낮았다.

[자체 거부 근거](native-rejections-001.json)는 18개 해당 영수증 전체를 담으며, 거부된 후보에 대한 외부 평가나 외부 정답 수는 사용하지 않는다. 제안되는 모티프 수가 현재 자체 엔진이 유력하게 보는 수와 멀다는 개발 근거다. 손실 문턱이나 입력을 바꿔서 이 실행을 사후 통과 처리하지 않는다.

## 002: 자체 엔진이 모티프 후보 묶음에서 고르는 두 번째 후보

v2는 모티프의 기하적 점수로 먼저 고른 수 하나만 검증하던 방식을 바꿨다. 최대6개의 서로 다른 모티프 후보를 사전 기물 검사한 뒤, 남은 허용 수 묶음을 한 번의 같은 깊이 자체 검색에 전달한다. 실제 반환된 승자에게만 완료 점수와 예상 수순을 연결하고 다른 후보에는 점수를 복제하지 않는다. 기존 0cp 기준·왕 안전·반복·전체 시간 상한은 유지했다.

같은24쌍을 새 `candidate-source-002`에서 실행했다. 이 입력은 이미001의 사후 감사에 노출된 개발 자료이며 새로운 미사용 검증이 아니다. 모든 자체48선택 완료 후8국면을 감사했고, 기능·해시 검사와 모든 엔진 정상 종료를 확인했다. [요약](comparison-002.json)과 [전체 자체 후보 근거](native-rejections-002.json)를 보존한다.

이번에는2~5개 수로 구성된 묶음 검색14개가 모두 같은 깊이를 완료했지만, 반환된14개 승자가 모두 0cp 기준 아래였다. 실제 선택 변경은 다시 **0/24**, 양쪽 native 기본 수도24/24 동일했고 실제 창의적 채택·다양성 증가는0이었다. 따라서 두 번째 후보도 사전 창의성 수용 조건을 통과하지 못했다. 외부 손실은 같은 선택이므로 양쪽 같았으며, 공통 완료 깊이는 국면별16~18이었다.

사전 검사에서 거부된41개와 묶음에서 반환되지 않은23개는 네이티브 평가를 받은 승자14개와 구분한다. 이 결과로 거부된 후보가 외부에서도 나쁜 수라고 단정하지 않는다. 해당 후보에 대한 외부 평가는 조회하지 않았다.

## 003의 사전 계약: 양쪽 실제 응수 위치 재검증

[v3 사전 선언](predeclared-v3.json)은 세 번째 실행 전에 별도로 고정했다. 앞선 두 실행의 조건과 실패를 덮어쓰지 않으며 같은24입력·같은 시간 상한·같은 사후 품질/실제 다양성 기준을 유지한다. 기존 루트 동일 깊이 검증에서0손실인 수는 종전 경로로 검증한다. 루트의 차이가10cp 이내인 새 수는 곧바로 채택하지 않고 추가 검증의 입구로만 사용한다.

실제 기본 수와 후보를 각각 둔 다음 위치에서 자체 엔진을 새로 시작해, 상대 수를 제한하지 않고 동일한 D−1 깊이를 모두 정확히 완료해야 한다. 두 결과를 원래 착수자 관점으로 바꿔 후보가 기본 수보다 낮지 않은지 다시 확인한다. 이 child 비교 손실0과 원래 root 손실을 따로 기록한다. 실제 응수의 수순으로 양쪽 정산·반복·왕 안전을 확인하고 후보가 선택된 모티프를 유지해야 한다. 기존 더 깊은 root 경고가 있으면 짧은 재검증으로 지우지 않는다.

하네스도 새 채택의 native 품질 증거를 별도 게이트로 검사한다. root/child 깊이·부호·원본 수순·자식 FEN/전체 이력·정확한 공통/최종 수순 일치와 부모 위치로 합친 수순을 구분한다. 실제 trace에 해당 unrestricted child 검색과 반환 수가 존재하는지도 확인한다. 다른 깊이의 수치를 빼서 손실0으로 표시하지 않는다.

001/002에서 사용자의 앱이 실제로 동시에 계산했는지는 확인되지 않았다. 이전의 모든 엔진 종료 확인은 검증이 소유한 프로세스에 한정한다. 부모 작업에서 사용자의 앱을 저장 후 닫은 것을 확인했지만003 시작 직전에 앱이 다시 열린 것을 관측했다. 앱은 그대로 두고 실행하며 실제 동시 연산 여부는 불명이다. CPU 격리·고정 주파수는 여전히 통제하지 않았으며 각 실행 내부의 양쪽 비교와 실행 간 차이를 구분한다. 개인 전체 대국은 수집하거나 증거에 넣지 않는다.

## 003 결과와 최종 적용 결정

세 번째 실행도 고정한24쌍의 자체 선택48회와8국면 사후 감사를 모두 완료했다. 기능·해시·전체 입력 검사와 소유 엔진 정상 종료를 확인했다. [전체 판정과 실제 시간](comparison-003.json), [모든 해당 자체 후보 영수증](native-rejections-003.json)을 보존한다. SF18 공통 완료 깊이는16~18이며 실제 선택이 양쪽 같아 외부 손실도 같았다.

이번 실제 묶음 검색은15회였다. Benko의3회는 양쪽 실제 child D4 검색도 완료했지만 기본 수보다 각각6·7·7cp 낮아 거부됐다. 요청 예산 안에서 검증을 끝내지 못한 후보1개도 채택하지 않았다. 실제 착수 변경은 다시 **0/24**, native 기본 수 동일24/24, 창의적 채택·응수 뒤 모티프 유지 선택·고유 착수 증가 모두0이었다. 새 native 품질 증거 게이트는 채택 사례가 없어서 공집합으로 통과했으므로, 이것을 실제 창의적 선택의 품질 검증 성공이라고 해석하지 않는다.

추가 구간의 실제 평균 경과 시간은 기준319.551ms·후보550.287ms, 최대는711.305ms·971.373ms였다. 창의성 단계18개 영수증의 최대는717.196ms이고 각각의 요청 예산을 넘긴 사례는 없었다. 전체 `engine_move`의 최대는 기준1767.107ms·후보2014.896ms로, 같은 요청 상한이 같은 실제 시간이나 엄격한 전체2초 상한을 뜻하지 않는다. 사용자 앱이 열려 있었고 CPU를 격리하지 않았으므로 시간 차이를 일반적 성능 수치로 해석하지 않는다. [세 실행의 전체 시간 영수증](timing-all-runs.json)도 별도로 기록한다.

세 실행 모두 사전 창의성 수용 기준을 충족하지 못했다. 따라서 최종 실전 기본값은 **`gambit_creativity.ENABLED=False`**다. 연구 구현과 거부 근거를 보존하며 기존 실전 수 선택을 유지한다. 실험003의 스냅샷에는 실험 당시의 `True`가 그대로 남아 있고, 최종 비활성 소스는 별도로 보존한다. 기력이나 창의성이 개선됐다고 주장하지 않는다. 다음 연구는 손실 문턱 완화가 아니라 자체 엔진이 유력하게 평가하는 수 안에서 의미 있는 모티프를 발견하는 후보 생성 방식의 개선이다.

## 재현 도구

`tests/gambit_creativity_validation.py`는 실제 두 정책 실행과 사후 공통 깊이 감사를 담당한다. `tests/gambit_creativity_validation_tests.py`의 최종9개 검사는 최종 안전 재선택을 창의적 착수로 잘못 세지 않는지, native 기본 수 드리프트를 귀속하지 않는지, 손실·메이트·부분 표본이 통과를 막는지 검사한다. 다른 모티프의 양수나 일반 정책이 만든 새 수로 창의성 귀속을 대신할 수도 없다. v3의 child 증거 부호·깊이·이력 혼합 반례와 실제 helper의 흑/백 제어 영수증도 검사했다. 이 기능 검사는 실제 엔진을 호출한 기력 증거가 아니다.

최종 비활성 소스의 전체 갬빗 검사364개가53.979초에 통과했다(`gambit-tests-release.txt`). 활성 v3의364개/53.647초는003 직전 별도 검사다. 더 앞선349개/42.338초와 boss88개/47.178초는 당시 소스의 결과로 보존하며 최종 버전 검사와 합산하지 않는다. 첫 개발 검사348개 중에는 실행 중 소스 수정과 겹친 무결성 실패1개가 있었고, 동결 후 재실행에서는 통과했다. 이 실패 로그도 원본 그대로 포함한다.

## 원시 증거와 복원

[증거 묶음](creativity-evidence.zip)은 기준 소스 ZIP,001·002·003의 원본 소스 manifest와 기준 대비 덮어쓸 파일, 각 실행의 입력·실행 하네스·원시 native/SF 로그·영수증·전체 보고서, 검사 로그를 포함한다. 세 실험은 하나의 고정 표본을 반복 사용한 개발 과정이며 독립 표본72개가 아니다.

기준 ZIP을 새 디렉터리에 풀고, 대상 후보의 `source-manifest.json`에 없는 기준 파일을 제외한 다음 그 후보의 `overlay/`를 덮어쓰면 각 실험 소스를 복원할 수 있다. 최종 실전 소스는003에서 명시된 기본 비활성 파일 하나만 바꾼다. [최종 소스 차이](release-source-difference.json)와 묶음 안 `source-restoration.json`은 이 관계와 복원한 모든 파일의 해시 검사 결과를 기록한다. 실행 바이너리는 묶음에 중복 포함하지 않으며 보고서의5011/SF18 해시로 식별한다. 개인 저장 대국은 포함하지 않는다.

[압축 무결성 영수증](archive-integrity.json)은 전체 ZIP의 SHA256과 크기, 항목별 해시·CRC 검사 및 실제 별도 경로 복원 검증을 기록한다. 원격 CI·커밋·사용자 앱의 최종 종료는 별도 마감 기록의 범위다.
