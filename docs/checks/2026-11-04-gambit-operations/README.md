# 희생 후 운영 연습: 실제 엔진 비교

2026-11-04. 실제로 기물을 내준 정규 수순 이후부터 시작해, 오프닝 자료가 끝난 뒤의 전개·공격·기물 회수·수비 전환을 검사한다. 시작 수순은 선언한 시험 자료이며 엔진이 그 희생을 스스로 선택한 것으로 집계하지 않는다. 제한한 분기는 종료 결과가 생기지 않으면 PGN의 `*`를 유지한다. 완주 대국·인간 평가·Elo 실험으로 해석하지 않는다.

## 비교 전 고정

`before-source.zip`과 manifest에 기존 실행 소스·오프닝 자료 226개 파일을 보존했다. 새 구현과 학습 자료가 추가되기 전 내용이며, 캡처 중 원본과 임시 실행 루트의 SHA256을 확인했다. 각 비교 버전은 전용 임시 소스 루트에서 실행한다.

`predeclared/fixtures.json`은 12개 시작 위치·시드·계산량을 정한다. 에번스·킹스·대니시·모라·스태퍼드·부다페스트·알빈·벤코·프롬을 포함한다. 에번스 `c3 Ba5`, 대니시 `Bxb2 d5`, 모라의 전개 이후 위치는 별도 시작 분기다. 이름이 있는 방어라고 최선의 방어로 간주하지 않는다. 모든 시작판은 표준 초기 위치에서 합법 수를 재생해 만들었고, 연습 측 차례이며 실제 순기물 열세가 100~200cp 이상임을 확인했다.

가족 분리 주석은 확정된 독립 커리큘럼에 맞춰 모라를 훈련, 부다페스트를 검증으로 정정한 후 전체 실행을 시작했다. 시작 위치·수순·시드·조건은 바꾸지 않았다. 최초 주석 파일도 보존한다. 벤코·프롬은 이번 운영 연습의 보류 계열이며, 실행 메모리에 기록되지 않아야 한다. 이전 순위 모델 실험의 분리와는 구분한다.

## 실제 실행 조건

- 자체 엔진: 활성 Regicide 실행 파일 SHA256 `5011da4c5e6ef01c452bd7125e4e22b372d2c9cfb858ed8759057325acb0e6ba`. 실행 파일과 C++ 코드는 교체하지 않는다.
- 연습 측: 실제 `HumanGame` 경로, 기준 탐색 1000ms 및 기존 추가 검사 상한 1000ms. 시간 제한 없는 연구 호출로 연출 대기를 제외하고 비교한다.
- 상대: 별도의 실제 Regicide가 매번 제한 없는 1000ms 탐색으로 고른다. 시작 수순 이후 상대 수를 강제로 지정하지 않는다.
- 각 분기: 연습 측 착수 최대 10회. 조기 종료는 실제 결과대로 남긴다. 자료 후보가 없는 위치와 기존 20반수 공격 창을 지난 수를 별도로 센다.
- 독립 감사: Stockfish 18, 1스레드·Hash 32MiB·기력 제한 없음. 이미 저장된 수를 최대 250ms·깊이 12의 같은 루트 두 탐색으로 평가해, 공통 완료 깊이의 정확한 점수만 비교한다. 연습 측 모든 수와 상대 첫 수 및 3수 간격 표본을 검사한다. 외부 엔진 수는 어느 플레이어의 착수로도 사용하지 않는다.
- 시험 전용 대국·엔진을 생성하고 종료한다. 사용자의 대국, 설정, 실행 중인 프로세스에는 접근하지 않는다. 다른 개발 작업이 병행되므로 착수 시간 수치를 일반적인 속도 비교로 해석하지 않는다.

## 기록과 해석

원본 UCI 검색·완료 패킷·반환 수, 전체 수 이력, PGN, 실제 정책 영수증, 자체 추가 예산, 독립 감사 패킷을 보존한다. 실제 선택 수가 같은 국면의 자체 UCI 반환에 있는지, 기준 탐색 예산이 보존됐는지, 선택과 기록이 일치하는지 검사한다.

기물 균형·전개된 경미 기물 수·왕 주변 공격·압박 변화는 관측치다. 기물을 교환해 전개 기물 수가 줄어드는 것이 반드시 운영 실패는 아니며, 기물을 되찾은 한 사례를 강제 회수 능력으로 표현하지 않는다. 외부 평가 손실과 자체 점수는 각각 내부 기준끼리 비교한다. 메이트 점수를 임의의 cp로 바꾸지 않는다.

첫 두 착수의 smoke는 `smoke-before-v1/`에 따로 보존한다. 전체 비교의 자료와 합쳐 독립 표본 수를 늘리지 않는다.

## 최종 v2 결과

최종 소스·오프닝 자료·연습 기억 232개 파일을 `after-source-v2.zip`과 manifest로 고정했다. 기존 기준과 최종 버전은 같은 검증기·시드·시작 위치·요청 예산으로 **각각 12분기·연습 측 120착수·상대 108착수**를 실행해 모든 기능 계약을 통과했다. 원본은 `native-before-v1/`과 `native-after-v2/`, 집계는 [comparison.json](comparison.json)이다. 현재 파일과 최종 스냅샷의 차이, 소스·실행 파일 불변, 소유 엔진 종료는 [verification.json](verification.json)에서 확인한다.

- 두 버전 모두 자료 후속 후보가 없는 위치에서 108착수를 실제로 수행했다. 시작 자료 뒤에도 자체 엔진으로 계속 운영했다. 선언한 희생 시점으로부터 20반수를 지난 수와 자료 종료 여부를 별도로 기록했다. 이 나이 표시는 이전 정책이 그 국면에서 실제 활성화됐다는 뜻은 아니다.
- 최종 버전은 115착수에 운영 영수증을 남겼다. 관측 목표는 전개 69회·기물 회수 33회·공격 유지 4회·정리 8회·수비 전환 1회다. 이는 국면 특징에 따른 정책 라벨이며 최선의 계획이라는 정답은 아니다.
- 실제 연습 기억의 후보가 조회된 수는 22회다. 이 중 16회는 자체 기준 수와 기억 후보가 이미 일치했고, 4회는 현재 자체 검증 후 기억 후보로 교체했다. 나머지는 조회와 실제 선택을 구분한다. 벤코·프롬 보류 계열에서는 기억 후보 조회가 0회였다. 이전에 실패한 24특징 순위 모델도 활성화 0회다.
- 새 운영 경로가 자체 기준 대신 선택한 수는 총 10회다. 기억 후보 4회·자료 후보 3회·새 국면 특징 후보 3회이며 모두 현재 자체 평가 하한·포획 검사를 통과했다. 새 특징 후보 3회는 각각 적용 손실 한도 0, 실제 자체 손실 0이었다. 다른 후보의 실제 자체 손실도 1~16cp로 선언된 목표별 한도 안에 있었다.

10개 실제 교체수를 선택이 끝난 뒤 다시 감사했다. 같은 실제 수 이력의 국면에서 자유 Stockfish·저장된 Native 기준수·실제 선택수를 각각 새로 분석해 세 탐색의 공통 완료 깊이에서만 비교했다. [substitution-audit-v2/report.json](substitution-audit-v2/report.json)은 9회 깊이 14·1회 깊이 13을 확보했고, 원시 UCI 로그와 입력 보고서 스냅샷을 보존한다. 선택 수의 자유 탐색 대비 손실은 0~48cp, 같은 국면의 저장된 Native 기준 대비 변화는 −127~+29cp였다. 아래에서 정의한 **추가 악화 경고 조건 0회·새 피메이트 0회**였고 감사 엔진도 종료했다. 이 독립 감사의 답은 어느 선택 엔진에도 입력하지 않았다.

문제를 발견했던 킹스의 정확한 `e4 e5 f4 exf4 Qg4 g5 Nf3 h6` 국면에서는 최종 버전이 Native 기준 `Bb5`를 보존했다. `Nc3`와 `Bc4`는 손실 한도 0을 넘겨 거절했다. 새 정책의 불필요한 양보를 실제 재현으로 차단한 사례다.

전체 착수의 외부 손실 150cp 초과는 기존 6회·최종 4회, 최대는 기존 293cp·최종 259cp였다. 기물 열세를 끝까지 회복한 분기는 기존 4개·최종 3개였다. 일부 수가 바뀌면 이후 위치와 상대 응수도 갈라지므로 이 숫자들을 기력 상승이나 회수 능력의 증명으로 해석하지 않는다. 기존 자체 기본 탐색의 약점도 남아 있다. 새 정책의 추가 악화는 위의 같은 루트 Native 기준 감사로 따로 구분했다.

상대 수의 표본 감사도 포함하므로 모든 대응이 완벽했다고 가정하지 않는다. 최종 기능 검증과 별개로, root의 관련 회귀 [root-regression-v2.json](root-regression-v2.json)은 191개 모두 통과했다. 정확한 킹스 실패 재현과 새 특징 후보 무손실 조건이 포함된다.

## 첫 통합 버전의 문제 발견과 수정

`native-after-v1/`의 12분기·120착수는 실행 계약을 통과했지만 최종 채택 근거로 쓰지 않는다. 단순 전개 형태를 이유로 현재 자체 기준수보다 평가가 낮은 새 후보를 허용한 문제가 독립 감사에서 드러났다.

킹스 갬빗의 실제 `e4 e5 f4 exf4 Qg4 g5 Nf3 h6` 뒤, 자체 기준 `Bb5` 대신 새 형태 후보 `Nc3`를 골랐다. 현재 Native 동일 깊이에서는 21cp 손실이었지만, 이미 저장된 같은 위치를 별도 Stockfish로 읽으면 완료 깊이 14에서 선택 수가 Native 기준보다 117cp, 외부 자유 탐색 기준보다 281cp 낮았다. `warning-audit-v1/`의 입력 스냅샷·세 탐색·원시 UCI 로그에 재현했다. 대니시의 다른 경고는 같은 Native 기준보다 1cp만 낮아, 기존 기본 탐색의 약점과 새 정책의 추가 악화를 구분했다.

`substitution-audit-v1/`은 첫 버전의 실제 교체 24회를 모두 별도 같은 루트의 자유 탐색·저장된 Native 기준수·실제 선택 수로 확인한 기록이다. 사전 정한 경고 조건인 ‘자유 최선 대비 150cp 초과 손실이며 Native 기준보다 100cp 이상 악화’는 킹스 한 건이었다. 새 피메이트는 없었다. 모든 외부 답은 착수가 끝난 뒤만 계산하며, 어느 선택 엔진에도 전달하지 않는다.

이를 반영해 최종 버전은 출처가 단순 `native_operations_geometry`인 후보에 **현재 자체 기준수 대비 손실 0**을 요구한다. 확인된 책·실제 분석 기억에는 목표별 기존 15/35cp 한도를 유지한다. 현재 자체 평가 자체가 정확하다는 보장은 아니지만, 일반적인 전개 취향을 위해 추가 평가 손실을 허용하지 않게 했다. 하위 운영 정책은 v2, 후속 검증 정책은 v3이며, 정확한 킹스 재현 회귀도 추가했다. 최종 소스는 `after-source-v2.zip`과 manifest에 별도 고정하고 동일 12분기를 `native-after-v2/`에서 다시 수행한다.

## 별도 수비 전환 기능 검사

첫 12분기의 목표 라벨에는 수비 전환이 나타나지 않았다. 이를 숨기거나 이미 확인한 것으로 표시하지 않고 `supplemental-predeclared/fixtures.json`에 별도 두 위치를 선언했다. 실제 희생 후 킹스의 `...Ng4, ...Qh4`, 프롬의 `Ng5, Qh5` 압박을 프로젝트에서 합법적으로 구성했다. 둘 다 비체크·100cp 실제 기물 열세이며, 새 정책의 순수 국면 특징만으로 수비 전환 목표가 선택되는 위치다. 해당 위치의 Native/SF 점수를 보기 전에 골랐다. 권위 있는 이론 수순이나 최선의 방어라고 주장하지 않는다.

최초 프롬 구도의 `...Qe7 Qh5`는 흑 나이트가 즉시 `Nxh5`로 퀸을 잡을 수 있어 진짜 수비 전환의 근거로 부적절했다. 그 실행은 `native-before-defense-v1/`에 전술 우선순위 대조군으로 보존하고 최종 수비 집계에서 제외했다. 해당 점수를 보고 다른 위치의 성능을 고른 것이 아니라, 직접 퀸 포획이 없고 순수 특징에서 같은 수비 목표가 선택되는 `...Ne8 Qh5`로 고쳐 새로운 [fixtures-v2.json](supplemental-predeclared/fixtures-v2.json)을 선언했다. 수정 위치의 Native/SF 점수는 선언 후에만 계산했다.

기존·최종 버전 각각 두 국면에서 연습 측 6착수, 총 12착수의 별도 기능 검사를 모두 통과했다. 두 버전의 실제 수순은 같았다. 킹스에서는 `Nf3` 이후 전개를, 수정 프롬에서는 `...h6` 이후 반격·교환을 실제로 수행했다. 새 버전은 수비 전환 목표 3회와 전개 목표 3회를 관측했고, 자체 기준이 적절한 상황에서 강제로 수를 바꾸지 않았다(대체 선택 0회). 프롬의 기억 조회도 0회였다. 따라서 새 정책이 최적의 수비를 발견했거나 강제 방어를 증명했다고 표시하지 않는다.

이 별도 기능 검사는 메인 12분기의 평균·표본 수와 합치지 않는다. 최종 비교는 [defense-comparison.json](defense-comparison.json), 원본은 `native-before-defense-v2/`와 `native-after-defense-v2/`에 구분한다. 분기 중 체크 회피 등으로 운영 후보를 사용하지 않은 수는 기본 자체 탐색으로 둔 채 보존한다.

재현:

```powershell
.venv-tests\Scripts\python.exe tests/gambit_operations_validation.py --source-root <보존한 소스 루트> --binary <활성 Regicide 실행 파일> --stockfish build-m2-opponents/stockfish18/package/stockfish/stockfish-windows-x86-64.exe --output <새 결과 폴더>
```

`native-support-v1.py`와 `validation-harness-v1.py`는 실행 전 고정한 검증기 소스다. 현재 검증기·보존본·실행 결과의 해시는 최종 검증 파일에서 확인한다.
