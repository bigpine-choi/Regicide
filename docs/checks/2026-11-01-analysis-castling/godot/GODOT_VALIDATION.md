# 분석 캐슬링의 Godot 검증

2026-11-01, Godot 4.7.2·Regicide 0.7.0-dev `build/regicide.exe`에서 합성 88개, 실제 엔진 연동 71개, 실제 Viewport 입력 디스패처 44개, 정상 대국 흐름의 Viewport 입력 114개 검사가 모두 통과했다. 새 프로젝트 복사본에서 편집기 캐시 없이 실행하는 검사도 통과했다.

```powershell
.\.venv-tests\Scripts\python.exe tests/analysis_godot_tests.py --godot C:/Users/hanso/Tools/Godot/Godot_v4.7.2-stable_win64_console.exe --binary build/regicide.exe --output build/analysis-castling-flow-final
```

편집기의 네 권리 선택은 백·흑 킹/퀸사이드에 각각 대응한다. 원래 칸의 같은 색 왕·룩이 있을 때만 설정할 수 있으며, 기물을 놓았다는 이유로 권리를 추정하지 않는다. 폰·나이트·비숍처럼 해당 왕과 원래 룩을 바꾸지 않는 편집은 기존 권리를 보존한다. 왕이나 해당 원래 룩의 칸이 바뀌면 관련 권리만 제거하며 되돌려 놓아도 자동으로 되살리지 않는다. FEN 불러오기와 체크 상태 왕복, 잘못된 FEN 권리를 렌더링에서 조용히 수정하지 않는지, 룩이 없으면 변경을 막는지 확인했다.

실제 엔진 연동은 백·흑의 양쪽 캐슬링 버튼 4개를 모두 실행해 왕·해당 룩의 도착 칸과 비워진 원래 칸, 양쪽 권리 소모, 무르기 후 전체 FEN 복원을 확인했다. 킹을 두 칸 끄는 기존 입력으로도 캐슬링과 룩 이동·복원이 되는지 확인했다. 체크 중, 기물에 막힘, 킹이 지나는 칸에 상대 공격이 있는 위치에서는 각 색·방향의 버튼이 실제 합법 수 목록에 따라 비활성화되는지 확인했다. 권리와 현재 합법 수는 별도로 취급하며 프런트엔드가 체크 통과 규칙을 다시 구현하지 않는다.

후속 실제 흐름 검사는 초기 배치에서 `e2e4 e7e5 g1f3 b8c6 f1c4 g8f6`를 Viewport 클릭으로 진행한 다음 백 킹을 e1→g1로 끌고, 흑 비숍을 비운 뒤 흑 킹도 e8→g8로 끄는 방법을 확인한다. 백·흑 시점과 일반/상대 이동량 0인 마우스 이벤트를 모두 사용한다. 폰을 지웠다가 복원한 배치에서 분석을 시작해 같은 전체 흐름을 반복했다. 캐슬링 버튼은 판 위 고정 영역에 두고 관리기의 한국어 불가 사유를 바로 보여 준다. 킹→자기 룩, 자기 룩→킹 입력은 관리기가 제공한 정규 캐슬링 합법 수가 있을 때만 연결한다. 권리 없는 같은 배치에서는 킹 두 칸 이동과 킹·룩 입력이 모두 거절되는지 확인했다. 이 114개 검사는 `analysis-castling-flow.txt`에 있다.

앞선 형세·끌기 검사도 이 실행에 포함된다. 형세의 백 기준 부호·탐색 중/완료·메이트·무승부·오래된 평가 무효화와 실제 추천 탐색의 평가 스트림, 클릭 누락 방지를 위한 지연 조회 회귀 검사를 유지한다. Viewport 입력 44개는 일반 상대 이동·상대 이동량 0인 포인터 이동, 판/목록의 끌기, 버리기·판 밖 놓기, Esc·창 밖 취소, 회전 좌표를 실제 입력 디스패처로 검증한다.

이 실행은 headless·합성 입력이며 실제 OS 포인터의 직접 조작 검증과 구분한다. 개인 대국 대신 임시 관리기·저장 폴더를 사용했고 기존 대국 상태와 저장 바이트가 바뀌지 않았는지 검사했다. 최종 결과는 각 단계의 `analysis-*.txt`에, 엔진 해시·경로 기록은 `analysis-integration.json`에, 파일 사본 해시는 `sha256.json`에 있다. `runner-before-flow-fix.txt`는 정상 흐름 보완 전의 실행 기록이다. `.log`만 `.txt`로 이름을 바꾸고 내용은 그대로 보관했다.
