# 노드 예산 증가의 효과와 한계

2026-11-04. **노드를 늘리면 개선되는 위치가 있었지만, 같은 엔진에서도 악화·정체가 나타났다.** 노드 예산 일괄 상향이나 퀸 방어 후보의 안정판 승격은 채택하지 않았다. 실제 대국 설정·시간 배분·실행 파일은 변경하지 않았다.

## 사전 고정 조건

- 이전에 선언한 전술 실패 네 위치, 반복 체크 위치, 기존 Nxe5 희생 대조군 총 여섯 위치. 모두 기존 개발 자료이며 결과를 보고 고르거나 새 미학습 자료로 부르지 않는다.
- 기존 `f893c6f` 실행 파일 SHA256 `15872d934b736d52c0e5d173c4023fbf27a1be3a17fa6d027e694b3be9947e57`, 퀸 방어 후보 `0058387` 실행 파일 `a92061204410a579c3a5a042cc2320445f494f66a9964dde1af0b92f344ce057`.
- 각각 100,000 / 1,000,000 / 3,000,000노드. 총 36회, 새 프로세스 순차 실행, 위치별 양팔 순서 교대. 양쪽 classical + activity, Hash16MiB. 후보만 `UseQuiescenceQueenDefense=true`. 생각 시간은 제한하지 않고 질의당 15초 비상 중단 한도만 둔다.
- 모든 자체 선택을 먼저 완료한 뒤 Stockfish 18로 사후 감사. Threads1, Hash32MiB, 강도 제한 해제, 질의별 Clear Hash, 깊이14·최대0.5초. 같은 시작판에서 자유 검색과 선택 수를 비교하고 공통 완료 정확 깊이만 사용했다.
- Windows 11, Ryzen AI 7 350(8코어/16논리CPU), 단일 검색. 코드·바이너리·입력 해시, 원시 UCI, 사전 manifest와 실제 결과를 [증거 ZIP](evidence.zip)에 보존했다. [파일별 해시 검증](evidence-manifest.json), [전체 요약](summary.json).

실제 36회 모두 정확히 선언 노드를 사용하고 합법적인 완료 결과·정상 종료 코드 0·판 이력 보존을 확인했다. 외부 감사 여섯 위치 모두 공통 깊이14, 정상 종료 코드0이었다. 총 약126초가 걸렸다. 이 검증은 대국이 아니며 승률·Elo 평가가 아니다.

## 결과

아래 값은 **같은 시작판의 외부 최선 수 대비 손실 cp**다. 작을수록 좋다. 각 셀은 **기존 / 퀸 방어 후보** 순서이며, 유한 깊이의 추정값이지 승리·무승부의 수학적 증명이 아니다.

| 개발 위치 | 10만 노드 | 100만 노드 | 300만 노드 |

| King's:9 | 281 / 281 | 281 / 0 | 0 / 0 |
| King's:11 | 245 / 245 | 42 / 190 | 42 / 42 |
| Morra:25 | 196 / 196 | 271 / 271 | 126 / 126 |

| 반복 체크 | 195 / 195 | 195 / 195 | 195 / 195 |

- **확대가 도움이 된 예:** King's:9에서 기존은 300만, 후보는 100만부터 `Qf5`를 선택했다. 이 위치의 같은 감사 손실은 281→0cp다. 특정 위치의 결과이며 후보가 일반적으로 세 배 효율적이라는 뜻이 아니다.
- **악화와 재개선:** Morra는 두 버전 모두 `Ne6 → Kh1 → Nd5`, 손실 196→271→126cp였다.
- **더 많이 읽고도 계속 악화:** 기존 Budapest는 `d6 → Re8 → Nb4`, 손실 0→50→186cp였다.
- **해결하지 못한 경계:** 반복 체크는 두 버전 모두 `...a3`를 유지했다. 완료 깊이는 5→7→8로 늘었지만 잘못된 선택은 그대로다.
- **희생 유지:** 기존 Nxe5 대조 수는 두 버전·세 예산 모두 유지했다. 한 대조군으로 전체 갬빗 기풍 보존을 주장하지 않는다.

후보를 기존과 **같은 100만 노드**에서 비교하면 King's:11은 손실42→190, Budapest는50→277cp였다. 두 위치 모두 사전 큰 악화 경고(후보 손실>150cp 및 기존 대비>=100cp 악화)를 충족한다. 앞선100ms 16판의 6승5무5패만으로 승격하지 않은 판단을 유지하며, 후보의 위험도 함께 기록한다. 300만에서는 후보의 Budapest 손실이186→50으로 줄고 나머지 다섯 위치의 선택 품질은 같았다. 이것도 보편적인 안전성 증명은 아니다.

## 비용과 개발 판단

| 노드 상한 | native 보고 탐색 시간 중앙값(12회) |
| --- | ---: |
| 10만 | 0.252초 |
| 100만 | 2.475초 |
| 300만 | 7.373초 |

여기 시간은 최종 UCI 패킷의 엔진 탐색 시간이다. `query.elapsed_ms`는 프로세스 시작·설정·종료까지 포함하므로 구분한다. 서로 다른 탐색은 노드당 작업량도 다르며, 같은 노드를 같은 CPU 시간으로 해석하지 않는다.

노드 확대를 배제하지 않는다. **국면 판단 개선과 계산 자원 확대를 함께 연구하되, 실제 이득과 시간 비용을 확인한 예산만 사용한다.** 구체적으로는 다음 순서다.

1. 이번 100만 노드의 후보 악화 원인을 완료 깊이 부족과 방어 확장 비용으로 나누어 진단한다. 기존 깊이에서 덜 정확한 선택을 남기는 비용을 줄이는 것이 우선이다.
2. 남은 시계 안에서 복잡한 전술·희생 후보에 더 배분하는 정책을 별도 실험한다. 노드 목표보다 실제 시간 상한·시계 여유를 우선하며 공격 후보 검증 예산도 함께 보존한다. 국면의 복잡성을 아직 신뢰성 있게 식별하지 못하므로 자동 확대를 완료한 것으로 주장하지 않는다.
3. 동일 시간에 더 많은 유효 탐색을 처리하는 최적화와, 더 오래 계산하게 하는 설정을 분리해 측정한다. 노드 숫자 자체나 명목 깊이를 목적 함수로 사용하지 않는다.

현재 코드는 다음 깊이의 반복 탐색을 **전부 완료한 뒤** 선택을 갱신한다. 미완료 작업은 총 노드에는 포함되지만 착수 결과를 갱신하지 않는다. 더 깊은 완료 결과도 근사 평가와 선택적 탐색을 사용하므로 수 품질이 단조롭게 좋아진다는 보장은 없다. 일반 게임 트리의 반례는 [Nau의 원논문(1980)](https://www.cs.umd.edu/~nau/papers/nau1980pathology.pdf)에 있다. 이 논문의 인공 게임 모형을 Regicide의 모든 국면에 적용한 것은 아니며, 위 판단은 실제 자체 비교와 별도로 구분한다.
