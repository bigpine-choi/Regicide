# 형세 평가: 활동성 항목과 사람 차례의 추가 탐색

## 적용 범위와 판단

게임의 수식 평가에 자체 작성한 기물 활동성, 서로 다른 색 비숍의 협력, 룩의 열린 파일 항목을 연결한다. 사람 차례의 화면 평가에는 최소 3초의 탐색 예산을 주고 완료한 깊이의 결과부터 전달한다. 실제 AI 착수 시간과 오프닝 다양성 정책은 유지한다. UCI 및 직접 평가 함수의 기본값은 기존 실험·모델 호환성을 위해 꺼짐이며 게임 앱이 지원되는 새 바이너리에만 `UsePieceActivity=true`를 설정한다.

같은 시간의 작은 개발 표본에서 새 선택의 질이 대체로 개선됐고 가장 큰 관측 퇴보는 동일 참조 평가 기준 23cp였다. 이를 근거로 앱에 제한적으로 적용한다. **전체 경기력 향상, Elo 상승, Stockfish급 평가 또는 기력 무손실을 입증한 결과는 아니다.** 큰 표본의 색 교대 대국과 독립적인 보류 국면 검증은 이번에 수행하지 않았다. C++ 엔진의 실제 착수는 계속 Regicide가 고르며 Stockfish는 아래 오프라인 진단에만 사용했다.

## 비교 조건

- 기준 코드: `e3bb33cb91e235b6e78f0252b0907be34d346304`. 실행 기준 바이너리는 당시 설치된 Regicide 0.7.0-dev의 복사본, SHA256 `edd950fb673cfca4134968b64cc5ef0f3d77eda698e9f40d2965170f143d6e6a`다. 이 작업에서 그 기준 실행 파일을 다시 빌드한 것은 아니다. 원래 빌드 출처는 동결한 classical profile에 연결한다.
- 활동성 후보 SHA256: `5011da4c5e6ef01c452bd7125e4e22b372d2c9cfb858ed8759057325acb0e6ba`. 비교 중 가중치·표본·바이너리·검색 소스 변경 없음. 후보 소스는 `candidate-source/`에 보존한다.
- 참조: 로컬 Stockfish 18, SHA256 `9bde420202717ce083412027fbfb8c5c935b537591d712be8a8a8bae92f6e8d6`, Threads 1, Hash 16MiB, 전체 기력. Chess.com의 서버 엔진·설정을 재현했다고 주장하지 않는다.
- Windows 11, AMD Ryzen AI 7 350, 물리 8코어/논리 16, Python 3.13.16, python-chess 1.11.2. 공유 컴퓨터이며 CPU 독점·외부 부하 통제를 하지 않았다.
- 고정된 공개 개발 국면 22개: 기존 profile 10개와 neural diagnostic 12개 전부. 백 차례 16개/흑 6개로 균형 표본이 아니다. 실제 개인 대국은 제외했다. 입력 원본 SHA256 `8f0d6ce8a03636b4f5b0f8ffd65bdffef8e2efc4a6932a1525d970b73f74ef00`.
- 기존/후보 각 1,000ms와 3,000ms, 참조 2,000ms. 국면마다 다섯 검색의 순서를 회전하며 순차 실행. 검색마다 해시 초기화·새 game token·전체 제공 이력 유지. Regicide는 기본 Move Overhead 20ms를 유지했다.
- 기본 110개 검색의 정확한 점수·깊이·합법 PV·최종 착수 일치를 확인했다. 달라진 선택은 같은 국면의 고유 착수당 참조 제한 검색을 한 번씩, 총 27회 수행했다. 총 137개 검색이 모두 검사를 통과했다.

## 결과

아래 cp는 **동일한 Stockfish가 두 후보 수를 각각 제한 탐색한 결과의 차이**이며 현재 둘 차례 관점이다. 엔진 간 cp를 뺀 오차가 아니다. 서로 다른 깊이에서 끝나는 유한 탐색이므로 실제 손실이나 최선수의 증명도 아니다. 변경되지 않은 선택은 표에서 제외한다.

| 비교 | 선택이 바뀐 국면 | 새 수 선호 >20cp | 기존 수 선호 >20cp | ±20cp | 평균 새 수 차이 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 기존 → 활동성, 각 1초 | 9 | 5 | 1 | 3 | +26.3cp |
| 기존 → 활동성, 각 3초 | 10 | 2 | 1 | 7 | +11.9cp |
| 기존 평가 1초 → 3초 | 5 | 3 | 0 | 2 | +27.4cp |
| 활동성 평가 1초 → 3초 | 3 | 1 | 0 | 2 | +6.3cp |

각 1초와 각 3초의 앞 두 행은 동일 예산의 평가기 비교다. 뒤 두 행은 연산 시간을 늘린 효과이며 같은 자원에서의 성능 향상으로 해석하지 않는다. 가장 큰 퇴보는 초기 국면의 `Nf3 → Nc3`: 참조 +34cp/깊이24 → +11cp/깊이22, 차이 -23cp였다. 3초의 다른 퇴보는 오픈 게임 `Bb5 → Nc3` -17cp, 흑의 폰 체인 국면 `e4 → Nb4` -7cp였다. 자세한 FEN과 양쪽 원본은 `comparison/review-examples.json`에 있다.

참조가 절대값 100cp 이상 우세를 준 9국면에서 기존 1초·3초와 후보 1초는 모두 같은 쪽의 부호를 냈다. 후보 3초는 8개 일치, 1개 중립이었다. **이 부호 일치만으로 정확하다고 볼 수 없다.** 특히 `8/5pk1/1p4p1/p2p3p/P2P3P/1P3KP1/5P2/8 w - - 0 38`에서 모두 Kf4를 골랐지만, 참조는 +324cp/깊이21, 기존은 +8cp/깊이11·13, 후보는 +8cp/깊이11 및 0cp/깊이12였다. 폰 엔드게임의 장기 우세 판단은 미해결이다. 폰과 왕만 남은 이 국면의 활동성 항은 0이며 후보의 추가 계산 비용과 완료 깊이 차이도 영향을 줄 수 있다.

## 계산 비용과 작은 예시

42 FEN을 순환해 모드별 100만 평가, 1천 회 예열, 순서 교대 6라운드를 실행했다. 정적 평가 호출 중앙값은 기존 92.07ns, 활동성 203.61ns로 **2.21배의 비용**이 들었다. 전체 탐색 속도나 기력을 뜻하지 않는다. 같은 1초의 평균 완료 깊이는 기존 7.00/후보 6.86, 3초에서는 7.86/7.82였다. 탐색 경로가 다르므로 노드 수나 깊이만으로 강도를 환산하지 않는다.

정적 평가 예시에서 막힌 룩과 반열린 파일의 룩은 기존에 모두 +6cp였지만 후보는 -26/-1cp로 구분했다. 막힌 비숍과 길이 열린 비숍도 기존 +342/+342cp에서 후보 +333/+348cp로 구분했다. 상대의 활동성도 함께 반영하므로 새 총점이 항상 기존보다 높아지는 것은 아니다. `static-examples.json`은 이러한 계산 원리를 확인하는 예시이며 기력 측정이 아니다.

## 검증과 보존

- 네이티브 10개 실행 파일: 206그룹, 690,964 assertions, 실패 0.
- C++/Python 평가 대조: 457국면 × 8설정, 3,656개 결과 정확히 일치. Python 14개 검사 통과.
- 실제 UCI 연결: 31그룹 통과. 모델·기물 가치 전용 경로는 활동성 옵션의 영향을 받지 않는지 별도로 검증했다.
- 실시간 평가 상태 24개, 생각 시간 27개 통과. 기존 대국 25개와 추천수 14개도 통과했으며 선택적인 실제 엔진 항목은 각각 1개 제외됐다.
- 실제 기준 엔진 helper에서 1.244초에 같은 국면 탐색이 진행 중이었고 3.112초에 완료했다. 이는 최초 평가 출력 지연 측정이 아니다. 착수 반환 32.7ms, 취소 helper 종료 53.0ms, 이후 20회 관측에서 옛 점수 유입 0. GUI·물리적인 화면 표시 검증과 구분한다.
- 측정 드라이버 16개 단위검사: 흑백 관점, 불완전/범위 점수 거부, PV 적법성, 변경 수 비교, 시간 예산 분리, 고정 입력 해시 등을 확인했다.
- 최종 앱 연결 이후 평가 상태 30개·생각 시간 27개 통과. 실제 후보·기존 바이너리·명시 신경망의 세 경로에서 각각 5개 factory와 상태/기보/코칭 평가 ID를 검증했다. 기존 probe 소비자도 2개 실제 검사 통과.
- 다음 실행용 설치 도구 17개 검사 통과. 경로 이탈·손상·실패 시 기존 선택 보존·Windows junction 거부·비 Windows 기본 경로를 확인했다. 실제 Linux 실행 검증은 수행하지 않았다.
- 설치된 SHA별 복사본으로 임시 대국을 시작하고 3초 평가 후 `e4 d6` 한 차례 진행, 합법 기보·평가 ID·1초 AI 설정·오프닝 v3 정책 유지 확인. 오프닝 회귀 검사 60개 통과. 실제 GUI 조작은 하지 않았다.

`comparison/`은 모든 품질 원본, `native/`는 비용·규칙·모델 호환 검증, `pipeline/`은 갱신 검증, `baseline/`은 기준 출처다. 기보 저장소나 실행 중인 사용자 게임을 수정하지 않았다. 기본 probe 출력은 기존 13열을 유지하고 `--piece-activity`에서만 17열을 내보낸다.

후보는 기존 `build/regicide.exe`를 덮어쓰지 않고 SHA별 별도 경로에 설치했다. 기존 두 사용자 프로세스와 기준 실행 파일의 SHA는 유지됐다. Godot·브라우저 실행기의 PowerShell 구문 검사를 통과했고 같은 resolver를 통해 새 경로가 선택됨을 확인했다. 다음 앱 실행부터 적용된다. `candidate-source/`는 측정 당시 소스, `application-source/`는 최종 앱 연결·실행기 소스다.

## 재현

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build.ps1 -BuildDirectory build-eval-activity -Test -EvaluationProbe
.venv-tests/Scripts/python.exe tests/classical_evaluation_tests.py --binary build-eval-activity/regicide.exe
.venv-tests/Scripts/python.exe tests/evaluation_quality_tests.py
.venv-tests/Scripts/python.exe scripts/check_evaluation_quality.py --baseline build/evaluation-quality-v1/baseline/regicide.exe --candidate build-eval-activity/regicide.exe --output build/evaluation-quality-v1/comparison-repeat
build-eval-activity/regicide_evaluation_benchmark.exe --activity tests/data/evaluation_profile_2026_10_18.fens
```

기준 바이너리는 위 해시로 보존한 로컬 복사본을 사용했다. 새 환경에서 기준 코드를 다시 빌드하면 그 바이너리의 별도 해시·도구 버전을 기록하고, 동일 실행 파일을 재사용한 것과 구분한다. `pipeline/real_helper_check.py`의 원래 실행 위치는 `build/evaluation-refinement/`이며 같은 위치에 복사해 재실행할 수 있다. 재실행 출력은 과거 원본을 덮어쓰지 않도록 별도 보관한다.
