# 반복 체크의 실제 평가 말단 진단

2026-11-04. 퀸 방어 후보와 별개로, 기존 탐색이 반복 체크의 탈출 반박을 어디서 놓치는지 관측했다. **반복 체크 문제는 해결하지 않았으며 체크 예산도 변경하지 않았다.** 개인 대국·게임 식별자·전체 이력은 포함하지 않는다.

최소 시작판은 다음과 같다.

```text
r4k2/2p5/1pqp4/5r2/p3R2R/2B3P1/PP3P1P/6K1 b - - 3 31
```

기존 `trace_gambit_leaf` 드라이버를 사용했다. 활동성 평가와 LMR은 켜고 나머지는 기본값이다. 실행 파일 SHA256과 각 요청은 [manifest.json](manifest.json), 전체 관측은 여섯 JSON에 보존했다. 기존 소스의 `StaticEvaluationObserver`가 **실제로 호출된 경로·반복 깊이만** 기록했다. 고정 깊이·노드 상한의 진단이며 벽시간 비교가 아니다. 관측 드라이버와 활성 UCI 엔진은 서로 다른 실행 파일이다. 전체 수 깊이 7의 수·점수·노드가 기존 기준 패킷과 일치함을 확인했지만, 이를 두 실행 파일의 완전한 소스 동일성 증명으로 해석하지 않는다.

| 검색 | 실제 결과 | 관측한 평가 호출 |
| --- | --- | --- |
| 시작판 전체 수, 깊이 7 | `...a3`, 흑 +441cp, 476,161노드 | 아래 두 말단을 각각 2회 관측 |
| `...a3 Rh8+ Kf7 Rh7+ Kg6` 뒤 `Rg7+` 한정, 깊이 1 | 백 −450cp, 238노드 | `Rg7+ Kh6 Re6+ Kh5` 뒤 −458cp, qply 3 |
| 같은 탈출 국면·같은 제한 수, 깊이 3 | 백 −45cp, 3,067노드 | `Rg7+ Kh6 Re6+ Kh5 g4+ Kh4` 뒤 −449cp, qply 3; 이후 포획까지 읽음 |

시작판의 전체 수 검색 깊이 7에서 실제로 다음을 관측했다.

- `...a3 Rh8+ Kf7 Rh7+ Kg6 Rg7+ Kh6`: 백 −450cp, qply 0, 무승부 조정 없음.
- 위 수순 뒤 `Re6+ Kh5`: 백 −458cp, qply 2, 무승부 조정 없음.
- 그 뒤 `g4+ Kh4`의 정확한 평가 호출은 관측되지 않았다.

기준 `src/search.cpp`는 비체크 안정화 노드에서 정적 평가를 후보로 두고, 경로당 조용한 체크 1회만 추가한다. 해당 경로에서는 `Re6+`가 그 예산을 소비하므로 다음 합법 수 `g4+`가 후보 필터에서 제외된다. 체크 회피 자체는 모두 남으며 체크 중인 위치에서 정적 평가를 사용한 오류가 아니다. 깊이 3의 짧은 별도 검색은 `g4+ Kh4 gxf5 axb2 Bxb2 Ra2`까지 읽으며 평가가 달라진다.

이는 **실제 정적 평가 호출과 누락되는 수의 증거**다. 관측된 호출 하나가 최종 루트 점수를 결정했다는 인과 증명은 아니다. 관측 0도 그 자체로 미탐색 증명은 아니며, 이 경우에는 소스의 정확한 체크 예산·필터 조건을 함께 확인했다. 깊이 1과 3은 같은 계산량 비교가 아니므로 성능 향상으로 해석하지 않는다.

새 퀸 방어 정책은 자기 퀸이 공격받는 첫 말단만 처리한다. 이 반복 체크의 위험은 별도 미해결 문제다. 단순한 전역 체크 증액·체크 확장·반복 점수 보정은 이 진단에 포함하지 않았고, 앞선 일곱 실패 후보는 [기존 기록](../../2026-11-04-perpetual-check/README.md)에 남아 있다.

`reproduce.py --binary <trace-driver> --output <새 폴더>`로 같은 여섯 요청을 실행할 수 있다. 이 래퍼는 수동 실행 후 같은 입력을 정리한 재현용 코드이며, 보존 결과를 래퍼로 다시 생성하지 않았다. 실행 전에 `--help`와 구문을 검사했고, 보존 JSON의 입력·PV 합법성·노드 상한·완료·판 보존·해시를 별도로 확인했다. 바이너리 자체는 보관하지 않는다.
